依据指定 [before.json](<D:/Code/dsh-plugins/dsh-superpower/docs/superpowers/verification/control-loop-corrections/routing/before.json>) 中的完整技能内容，各场景的下一步决策如下。

**A**

- **采取的动作：** 直接进入已呈现并获认可的有界修改，修改现有配置读取逻辑，随后运行现有回归。
- **暂停范围：** 无需暂停或再次请求同一授权。
- **后续反馈：** 检查实际差异与回归结果；失败则据反馈重新诊断，成功后报告已验证的行为。
- **依据：** 有界路径要求用户认可对话内设计；“开始修正”已满足这一门槛。范围和风险未变，已有授权覆盖当前动作。

**B**

- **采取的动作：** 保留已经选定的架构性路径，从最早尚未完成的阶段继续；将方案内容收缩为复用已有模块、修正参数映射，保持原验收标准。
- **暂停范围：** 实现等待架构性路径要求的规格认可、计划审阅及执行方式确定；只读调查和必要的规格、计划准备可以继续。
- **后续反馈：** 向用户呈现已有模块的调查证据及实际最小改动，使其评审相应产物；进入实现后验证参数映射和原验收。
- **依据：** brainstorming 明确规定“任何情况下都不中途降级”，且架构性路径要求完成书面规格与实现计划的门槛。新增证据用于精简方案内容。

**C**

- **采取的动作：** 说明第一、第二项已经理解，先请求澄清第三项数据保留期限的准确含义，以及它对接口重命名的影响。
- **暂停范围：** 暂停三项的实现，包括独立的文档链接修复；可继续只读核查。
- **后续反馈：** 取得澄清后核对第二、第三项的共同契约，再逐项修复、逐项验证，最后检查回归；链接项检查目标及引用。
- **依据：** receiving-code-review 对多事项反馈明确要求，任一事项含义不清时“先不要实现任何东西”，并要求先澄清所有不清之处再实现。

**D**

- **采取的动作：** 停止继续叠加修复，向用户报告运行进程加载旧产物的新证据，并讨论原先的验证假设与是否有架构问题；继续只读确认进程、加载路径和产物版本。
- **暂停范围：** 暂停第四次修复，直到完成该版本要求的架构层面讨论；不暂停证据收集，也不直接开展架构重构。
- **后续反馈：** 讨论后先确认运行实例实际加载正确产物，再按原场景复测，区分旧产物造成的无效反馈与仍然存在的缺陷。没有耦合或新症状的证据，就不宣称架构缺陷已经成立。
- **依据：** systematic-debugging 明确规定，三次修复无效后必须停下来质疑架构，“没有架构层面的讨论，不要尝试第 4 个修复”；同时要求先调查根因、确认实际路径触达。

**E**

- **采取的动作：** 将规格中的新导出接口名同步到计划所有受影响的下游引用、消费与产出接口及示例，消除已经发现的不一致，完成可实施的规格和计划。
- **暂停范围：** 暂停受影响计划的交接和执行，直到这些已知矛盾修正；无需为同步引用另行请求授权，也不重启完整自审。
- **后续反馈：** 向用户交付命名一致的规格与计划，进入原流程要求的规格或计划审阅；说明接口名和下游引用已同步，不把尚未执行的实现验证说成通过。
- **依据：** writing-plans 要求作者解决方案歧义，明确检查前后任务的类型、方法签名与属性名一致性；发现问题就地修正，“不需要重新自检——改完继续往下走”。
