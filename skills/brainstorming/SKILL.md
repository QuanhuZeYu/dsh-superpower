# 把想法头脑风暴为设计

通过协作式对话，把想法变成与使用者达成共识的设计与规格。先按复杂度分类路径，再沿路径推进。

## 三条路径与分类边界

提问前先探索仓库现状，声明路径分类及依据（使用者可推翻）：

| 路径 | 适用条件 | 核心步骤与交付物 |
| --- | --- | --- |
| **探针（Spike）** | 可行性验证（“能不能……”），产出是答案而非保留代码 | 框定上下文 → 2-3 句话说明问题与探针方案 → 核对授权 → 最省调查 → 汇报建议（顺手代码标为一次性丢弃） |
| **有界（Bounded）** | 仓库已有可改流程，做范围清晰的局部改动（新开关、小接口、单文件行为调整） | 探索上下文 → 问关键澄清问题（一次一个）→ 对话内呈现简短设计（方案/文件/测试）→ 核对授权与输入 → 按开发模式直接实现（无规格与计划文档） |
| **架构性（Architectural）** | 新项目、新子系统、跨组件重组或修改公共依赖接口 | 探索上下文 → 澄清目的与约束 → 比较备选方案（推荐置顶）→ 分节呈现设计 → 写规格文档并提交 → 规格自审与交接 → 加载 `writing-plans` |

- **可逆文档维护豁免：** 纯错字、格式、链接或翻译修正，不改变行为、契约或风险且已获授权时，直接读取修改并核对 diff，跳过本流程。
- **动态升降级：** 执行中发现隐藏依赖或范围扩大时，立即停止扩大改动、重新分类并从对应门槛开始；证据表明可复用现有模块且影响局部时可降级。若请求包含多个独立子系统，先拆分为独立子项目，逐个走“规格 → 计划 → 实现”循环。

## 从简设计与沟通判据

先定目标语义与不变量，再定职责与协作，最后选接口与字段：

- **职责句统领设计：** 每项先用短句写清“谁决定、谁执行、谁提供事实、何时生效”，再用具体情景解释结果（业务选策略，框架护不变量，适配层供外部事实）。不以“自动协调”隐含未声明的重试或迁移能力。
- **先减分支，机制对应真实问题：** 优先收束业务分支（删减已要求能力须经裁定）；新机制与扩展点仅服务已知需求或真实运行边界，严守 YAGNI。可变状态靠变化通知与有界可失效缓存维护，不靠每次全量重算。
- **代理承担普通技术判断：** 已有授权和契约内的可逆细节由代理自行决定。仅将改变目标、用户行为、核心边界或长期承诺的取舍交给用户。
- **逐项裁决格式：** 用户要求逐项裁决时，每条消息只问一个问题，采用“职责句 → 触发情景与结果 → 推荐及代价 → 一个问题”（优先选择题）。目的与约束已清晰时直接简述理解供确认，不为维持对话制造议题。

## 规格写作与隔离设计（架构性路径）

将达成共识的规格写入 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`（用户指定路径优先）并提交 git。

- **主线清晰，合同归位：** 规格写清目的、选定方向、模块职责、主流程/高层伪代码、已知失败归属及下一步反馈方式。同一要求在所属规格维护，其他模块引用；接口细节与容错机制随对应专题细化。
- **区分预期缺口与程序错误：** 外部输入与 I/O 在负责边界校验，下游直接消费契约。允许部分处理时保留可用部分并记录缺口；内部非预期异常与不变量违反记录上下文后及时上抛，禁止吞异常或造假默认值。
- **单元隔离与顺手治理：** 拆分职责单一、接口清晰、可独立理解与测试的小文件单元。遵循既有代码库模式；触碰已臃肿纠缠的文件时将针对性拆分纳入设计，但不提议无关重构。
- **过程信息归位：** 阶段范围与后续专题在开头说明一次，运行结果放验证记录；正文直接写产品行为，删除重复的“未授权 / 不能保证”免责声明。

## 规格自审与阶段交接

写完规格后就地自审并修复：
1. **完整性与无歧义：** 主流程、职责清晰，无 `TODO / TBD` 占位符；存在两种解释的需求选定一种写死。
2. **内部一致与范围聚焦：** 章节无矛盾，高层方向与后续专题边界清楚。
3. **零施工噪音：** 删除无具体失败路径依据的防御要求与重复免责声明。

**交接边界：** 探针交付结论，有界工作按授权实施，架构性工作交付规格链接。用户要求审阅规格时等待回复；已授权自主推进时直接加载 `writing-plans` 编写实现计划（设计授权本身不自动扩大为实现授权）。

## 常见误区对照

| 误区 | 实际规则 |
| --- | --- |
| “太简单了，不需要设计” / “换个有界标签跳过规格” | 有界改动也要给对话内简短设计；是否属于有界取决于仓库中是否已有可改的现成流程，而非你的熟悉度。 |
| “探针跑通了，直接把代码留下” | 探针只交付答案；保留代码属于新请求，须重新分类设计。 |
| “认可了探针或前序任务，后续改动自然算认可” | 每个任务与路径升级都有独立的分类和授权边界。 |
