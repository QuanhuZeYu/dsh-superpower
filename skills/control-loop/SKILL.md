# 控制论：以反馈驱动任务收敛

Superpowers 的核心哲学是控制论。技能是可调整的控制策略，工作成果由用户目标与可核实的反馈判定。

**观测 → 判断状态与误差 → 采取最小有效动作 → 验证反馈 → 修正 → 重复；达到验收条件后停止。**

## 建立最小闭环

在首次改变状态前明确下面的信息；简单任务在对话中简述，多步骤任务放进现有清单，不另造仪式性文档。

| 要素 | 必须回答的问题 |
| --- | --- |
| 目标与边界 | 用户需要什么可观察结果？授权范围、不能破坏的约束是什么？ |
| 当前状态 | 已观察到什么？哪些是推断，哪些仍未知？证据对应哪个版本和环境？ |
| 误差 | 当前结果与验收标准具体差在哪里？信息缺口也要明确。 |
| 动作 | 哪个最小、可验证的动作能缩小误差或区分竞争假设？ |
| 反馈 | 从哪里取得结果，何时应当出现，什么现象会推翻当前判断？ |
| 退出 | 何时完成、重评、回退，或因缺少必要输入暂停？ |

定性任务可以用具体示例、验收清单和人工检查建立反馈，不必强造数值指标。

## 七条行动原则

1. **先观测，后行动。** 区分事实、推断与目标；未知不等于失败。
2. **以误差驱动。** 每个动作说明它要消除什么差距或不确定性；不能只因为计划里写了就做。
3. **小步控制。** 优先局部、可逆、可验证的动作。先试探再扩大；动作幅度与风险、证据强度相称。
4. **行动必须有反馈。** 工具返回成功只证明该操作的有限结果，验收还须检查目标状态。
5. **异常立即重评。** 反馈与预测不符时，暂停依赖该判断的后续动作，重新观测和定位原因。
6. **避免过度控制。** 确认、计划、技能加载、评审和测试都有成本，按风险与剩余不确定性选取。
7. **持续收敛。** 让实际结果稳定接近目标；满足验收后收尾，不为局部完美继续扰动系统。

## 让反馈可信

- **目标、观测、误差分开。** 测试结果和构建日志是观测；与验收标准比较才产生误差判断。测试通过不能替代用户目标。
- **可观测性与可控性分开。** 看得到不代表改得动，改得动不代表能验证。缺少反馈时先补观测；缺少权限或执行通道时报告具体限制。
- **检查证据覆盖。** 单元测试通过不能外推性能、并发或页面体验；结论只覆盖实际验证的版本、环境和行为。
- **避免自证。** 用需求示例、真实输入和独立来源核对结果。涉及重大行为或难以自查的风险时引入独立评审；不同上下文仍可能共享同一错误假设。
- **验证观测通道。** 若测试从未证明能捕获目标缺陷，使用已知反例或在隔离环境做可恢复的扰动。不要在真实用户环境故意制造故障。
- **目标变化时重设回路。** 根据新需求更新验收标准、受影响计划和测试；不能为了让失败消失而降低标准。

## 延迟、噪声与停滞

| 观察到的状态 | 下一步 |
| --- | --- |
| 后台任务仍在运行、反馈尚未到达 | 保留任务标识，等通知或在阻塞时取结果；继续独立工作。未判明失败前不重复启动。 |
| 超过工具或任务约定的预期时间 | 检查状态与日志，确认挂起、失败或仅仅延迟；根据证据决定等待、取消或重试。 |
| 结果偶发波动或互相矛盾 | 控制环境与输入，检查样本和测量方式；用有理由的复测辨别噪声，不凭一次波动扩大改动。 |
| 同一动作反复无新证据，或方案来回切换 | 停止原样重试；列出已排除假设，换一个能区分原因的观测或缩小实验范围。 |
| 权限、工具、外部依赖限制已明确 | 不加大动作绕过限制；做独立且已授权的工作，说明缺失能力或必要输入。 |

对昂贵或可能反复的调查，预先给出与任务相称的尝试范围或资源预算，以及耗尽后的交接方式。预算耗尽触发重评和如实报告，不代表目标已完成。没有新证据，不扩大同一种干预。

## 回退与授权

备份、提交和开关只有确实能恢复受影响状态时才构成回退方案。**dry-run 是预检，不是回退；本地备份不能撤销远端副作用。** 无法回退的动作须明确影响、验证渠道和失败后的处置，并按当前会话授权规则执行。

已有授权在其范围内持续有效。可逆的已授权工作直接推进；关键需求缺失、范围扩大或确需额外授权时，先把可独立完成的准备工作做成可评审结果，再提出具体问题。技能不增加高于系统、开发者或用户指令的权限，也不要求重复授权。

## 完成与暂停

- **完成：** 验收标准均有相应证据，关键反馈已收集，相关后台任务已收尾，残余限制已明确披露。停止增加无关改动。
- **继续：** 仍有目标差距，且存在已授权、能取得新证据或缩小误差的动作。
- **暂停依赖步骤：** 必要输入、授权或能力缺失；明确缺什么、影响什么。未验证项不能包装为完成；独立工作可以继续。

示例：修复保存按钮后构建通过，但尚未检查用户页面。剩余误差是保存行为未知；下一步在目标页面操作并检查持久化结果。若构建仍在后台运行，先收集原任务结果，再验证依赖它的页面。保存成功且相关验收通过后收尾。

## 与其它技能协作

| 技能 | 回路职责 |
| --- | --- |
| `using-superpowers` | 按当前任务与证据选择所需技能 |
| `brainstorming`、`writing-plans` | 把意图变成验收标准，规划可验证的小步 |
| `test-driven-development` | 实现与行为测试之间的局部反馈 |
| `systematic-debugging` | 用实验区分根因假设 |
| `verification-before-completion` | 核查完成结论的证据与适用范围 |
| `subagent-driven-development`、`dispatching-parallel-agents` | 隔离工作，收集独立反馈，核对集成状态 |
| `finishing-a-development-branch` | 验收后的交付与收尾 |

流程冲突时先遵循上级指令，再结合任务范围选择能保持反馈有效的最小流程；不得用“控制论”作为跳过必要验证或授权的理由。
