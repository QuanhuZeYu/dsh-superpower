# 执行计划（内联）

在本会话内亲自逐个任务执行计划，不为单任务派发子代理或评审者；整条分支在最后做一次全新上下文的评审。

**核心原则：** 简报是规格，台账是持久记忆，运行证据是单任务门禁，最终评审是独立把关。工具调用之间最多用一行短话说明；冗长测试输出重定向到工作区文件后只读尾部。

## 准备与恢复核对

1. **隔离工作区：** 按 `using-git-worktrees` 创建或核验隔离 worktree；未经明确同意，绝不在 `main/master` 上直接实现。
2. **定位计划工作区与台账：** 与 `subagent-driven-development` 共用目录和格式（支持中途切换执行方式）。运行 `python ../subagent-driven-development/scripts/sdd-workspace.py PLAN_FILE` 定位目录，台账首行为 `# SDD 台账 — 计划：<计划文件路径>`。
3. **恢复核对（上下文压缩或重入时）：** 比较计划/规格版本、任务文本与验收；确认完成提交仍在当前历史且未被覆盖或破坏；检查工作树、依赖配置及原始证据失效条件。记台账 `恢复核对：<版本>；<验收>；<提交与工作树>；<证据及失效条件>；<沿用/重开及理由>`。仅跳过验收与证据仍有效的任务。
4. **预检扫描与建待办：** 通读计划与 Spec（冲突裁决以 Spec 为最高权威；无 Spec 时注明裁决为临时）。对照计划 `Interfaces` 块扫描跨任务共享接口冲突，每对共享接口记一行台账（无共享则记 `预备检查：无共享接口`），对冲突作出裁决后，用 `todo_write` 为所有任务建待办。

## 任务循环

每个任务开始前按简报加载 `test-driven-development` 或 `runtime-driven-development`（缺失时按 `using-superpowers` 选定并记台账）。记账与 commit 合并在同一次调用中完成，不单独开回合。

### 1. 启动任务
运行 `python scripts/task-start.py PLAN_FILE N` 获取简报路径与 `BASE` commit。必读简报原文（取精确签名、数值与用例），将对应 todo 标为 `in_progress`。

### 2. 逐步执行与比对
按所选开发模式跑通最小真实路径并验证反例/实机探针（已有行为满足契约则如实记录，不人为造红）。将每步真实输出与简报 `预期：` 比对：
- **一致：** 进入下一步。
- **代码错误：** 加载 `systematic-debugging` 定位并修根因，绝不修补症状凑输出。
- **计划错误（与 Spec 或前序接口冲突）：** 作满足 Spec 的最小裁定，记台账 `任务 <N>：裁决： <发现> — <决定及理由>` 后继续。

按计划提交（评审范围从 `BASE` 切，不用 `HEAD~1`）。

### 3. 完成契约与记录
使用 `verification-before-completion` 核验：简报要求的自动检查或实机操作已在当前版本执行、原始反馈可复核、所有 `预期：` 已比对、所有偏离已记 `裁决：`。
- **有自动测试命令：** 运行 `python scripts/task-done.py PLAN_FILE N BASE -- <测试命令>`（命令通过时自动把 `任务 <N>：完成（commits <base7>..<head7>，tests: <command> → <result>）` 追加到台账；严禁用空命令或打印 PASS 伪造）。
- **含手动 UI/设备实测：** 核对原始记录后在台账写明 `任务 <N>：完成（commits <base7>..<head7>，runtime: <实例/场景> → <实际结果>，evidence: <记录位置>）`。
- 核对完整验收与失效条件后，将 todo 标为 `completed`。

## 最终评审与收尾

1. **生成评审包：** 运行 `python ../subagent-driven-development/scripts/review-package.py PLAN_FILE MERGE_BASE HEAD`（如 `git merge-base main HEAD`）。
2. **整分支评审：**
   - **有 `subagent` 工具：** 显式指定最强 `model`，用 [code-reviewer.md](../requesting-code-review/code-reviewer.md) 派发评审子代理，传入评审包、计划与 Spec 路径、`Review Focus` 及台账 `裁决：` 位置。
   - **无 `subagent` 工具：** 对照 `code-reviewer.md` 与评审包独立自审，台账记 `Final review: self-review (no subagent tool)` 并在最终消息告知使用者。
3. **分诊与修复：**
   - 凭具体触发路径与运行证据分诊；任何轮次均可凭反证驳回误报（记 `终稿：裁决：<发现> — <反证与版本> — <影响>`）。
   - **Critical / Important：** 按任务开发模式修复、实测并跑回归，默认先做一次集中修复。内部预算用尽仍未收敛时，重评并换策略继续；仅用户/工具硬预算耗尽，或核实确缺外部输入、权限或资源时交接。验收未满足则保持未完成。
   - **Minor：** 台账记 `终稿：次要（暂缓）： <一句话>`，不进修复轮。
4. **存档与汇总交付：**
   - 在最终消息中完整列出所有 `裁决：`（「我做过的裁定」，附错了的代价）与所有暂缓项（「推迟的 Minor」）。
   - 将台账与原始验证记录存档到持久位置并确认可打开后，删除本计划临时工作区，加载 `finishing-a-development-branch`。

## 常见误区对照

| 借口 | 实际规则 |
| --- | --- |
| “我记得任务内容 / 最后再统一跑测试” | 记忆只是摘要，必读简报；逐步验证才能定位哪一步引入破坏。 |
| “我自己仔细读过 diff 了，跳过最终评审子代理” | 同一作者有相同盲点；最终评审是内联模式唯一一次全新上下文把关。 |
| “顺手把 Minor 也修了” | 每个未要求的修改都会增加额外测试与回归成本；记入台账交使用者决定。 |
