# 接收代码评审

**核心原则：** 先核实再实现，先澄清再假设；技术正确性高于社交寒暄，行动重于表态。

## 响应流程与沟通纪律

1. **通读并核查：** 对照代码库实际上下文、兼容目标与既有契约验证每条反馈。
2. **禁止表演式寒暄：** 严禁回复“你完全正确！”、“太棒了！”、“谢谢指正！”或冗长道歉。
   - **反馈正确：** 直接修改代码，回复“已在 `[位置]` 修复 `[具体问题]`”。
   - **反驳后发现自己错了：** 平实说明“核查了 `[X]`，确实存在 `[Y]`，已修复”，不找借口辩解。

## 按反馈来源与状态分诊

### 1. 含义不清的多事项反馈
核对事项间的契约依赖：对**已明确、独立且已授权**的事项立即修复并测试；仅暂停**含义不清或依赖未决契约**的事项，并一次性提出具体澄清问题。

### 2. 外部评审者建议（保持怀疑，严格核查）
实施前检查五项：(1) 技术上是否成立；(2) 是否破坏现有功能或历史兼容性；(3) 原实现是否有特定原因；(4) 是否违反 YAGNI（如建议“完整实现某端点”，先用 `grep` 查全库，若无调用方则提议直接删除而非扩写）；(5) 是否与使用者的架构裁定冲突。
- **何时反驳：** 建议破坏兼容性、缺乏上下文、违反 YAGNI 或技术有误时，用具体代码引用、测试结果或兼容约束直接反驳；涉及架构冲突时交使用者裁决。

### 3. 多事项实施顺序
按 **阻塞性问题（破坏/安全）→ 简单修复（错字/import）→ 复杂逻辑重构** 顺序逐项修改，每改一项单独验证测试，确保无回归。在 GitHub 回复行内评审时，直接回复在对应 comment thread（`pulls/{pr}/comments/{id}/replies`），而非顶层评论。
