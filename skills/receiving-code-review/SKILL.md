# 接收代码评审

## 概览

代码评审需要的是技术评估，而不是情绪表演。

**核心原则：** 先验证再实现。先提问再假设。技术正确性高于社交舒适。

## 回应模式

```
当收到代码评审反馈时：

1. 阅读：完整读完反馈，先不做反应
2. 理解：用自己的话复述需求（或提问）
3. 验证：对照代码库的实际情况核查
4. 评估：对这个代码库而言，技术上成立吗？
5. 回应：给出技术性确认，或有理有据的反驳
6. 实现：一次一项，逐项测试
```

## 禁止的回应

**绝不：**
- “你完全正确！”（明确违反指令文件）
- “说得好！” / “反馈太棒了！”（表演式）
- “我这就把它实现掉”（在验证之前）

**而应：**
- 复述技术要求
- 提出澄清性问题
- 如果建议是错的，用技术推理反驳
- 直接开始做事（行动 > 言语）

## 处理含义不清的反馈

```
如果任一事项含义不清：
  停下 —— 先不要实现任何东西
  就含义不清的事项请求澄清

原因：各事项之间可能相互关联。部分理解 = 错误实现。
```

**示例：**
```
使用者：“修复第 1-6 项”
你理解了 1、2、3、6，对 4、5 不清楚。

❌ 错误：现在就实现 1、2、3、6，稍后再问 4、5
✅ 正确：“我理解了第 1、2、3、6 项。继续之前需要澄清第 4 和第 5 项。”
```

## 按来源分别处理

### 来自使用者
- **可信** —— 理解之后即可实现
- 如果范围不清，**仍然要问**
- **不要表演式认同**
- **直接进入行动** 或给出技术性确认

### 来自外部评审者
```
实现之前先检查：
  1. 检查：对这个代码库而言，技术上正确吗？
  2. 检查：会不会破坏现有功能？
  3. 检查：当前实现当初为什么这样写？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：评审者了解完整上下文吗？

如果建议看起来是错的：
  用技术推理反驳

如果无法轻易验证：
  如实说明：“没有 [X] 我无法验证这一点。我应该[调查/询问/继续]吗？”

如果与使用者此前的决定冲突：
  先停下来，与使用者讨论
```

**使用者的规则：**“外部反馈 —— 保持怀疑，但仔细核查”

## 对“专业级”功能的 YAGNI 检查

```
如果评审者建议“把它正经实现”：
  用 `grep` 工具检索代码库中的实际用法

  如果无人使用：“这个端点没有被调用。删掉它（YAGNI）？”
  如果有人在用：那就正经实现
```

**使用者的规则：**“你和评审者都向我汇报。如果我们不需要这个功能，就不要加。”

## 实现顺序

```
对于多事项反馈：
  1. 先澄清所有含义不清之处
  2. 然后按此顺序实现：
     - 阻塞性问题（破坏、安全）
     - 简单修复（错别字、import）
     - 复杂修复（重构、逻辑）
  3. 逐项单独测试每个修复
  4. 验证没有回归
```

## 何时应当反驳

在以下情况反驳：
- 建议会破坏现有功能
- 评审者缺乏完整上下文
- 违反 YAGNI（无人使用的功能）
- 对这套技术栈而言技术上不正确
- 存在历史遗留/兼容性原因
- 与使用者的架构决策冲突

**如何反驳：**
- 用技术推理，而不是防御姿态
- 提具体问题
- 引用可正常运行的测试/代码
- 若涉及架构，请使用者参与

**如果你不好意思把反驳说出口：** 说出这种紧张感，然后把你看到的问题告诉使用者。他们会感激你的坦诚。

## 确认正确的反馈

当反馈确实正确时：
```
✅ “已修复。[变更内容的简要描述]”
✅ “发现得好 —— [具体问题]。已在 [位置] 修复。”
✅ [直接修好，并在代码中体现]

❌ “你完全正确！”
❌ “说得好！”
❌ “谢谢你抓到这一点！”
❌ “谢谢[任何事]”
❌ 任何表达感谢的说法
```

**为什么不说谢谢：** 行动会说话。直接修就好。代码本身就表明你听进去了反馈。

**如果你发现自己正要写下“谢谢”：** 删掉它。改为说明修复内容。

## 得体地纠正自己的反驳

如果你反驳了，但自己错了：
```
✅ “你是对的 —— 我查了 [X]，它确实 [Y]。现在开始实现。”
✅ “验证过了，你是对的。我最初理解错了，因为 [原因]。正在修复。”

❌ 冗长的道歉
❌ 为你当初为何反驳辩护
❌ 过度解释
```

平实地说明更正，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式认同 | 说明需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 不测试就批量改 | 一次一项，逐项测试 |
| 假定评审者一定对 | 检查是否会破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实现 | 先澄清所有事项 |
| 无法验证却继续推进 | 说明局限，请求指示 |

## 真实示例

**表演式认同（坏）：**
```
评审者：“删除遗留代码”
❌ “你完全正确！我这就把它删掉……”
```

**技术性验证（好）：**
```
评审者：“删除遗留代码”
✅ “正在检查……构建目标是 10.15+，这个 API 需要 13+。为了向后兼容需要保留遗留代码。当前实现的 bundle ID 是错的 —— 是修它，还是放弃对 13 以下版本的支持？”
```

**YAGNI（好）：**
```
评审者：“实现一套正经的指标跟踪：数据库、日期筛选、CSV 导出”
✅ “用 `grep` 工具检索过代码库 —— 没有任何地方调用这个端点。删掉它（YAGNI）？还是有我没发现的用法？”
```

**含义不清的事项（好）：**
```
使用者：“修复第 1-6 项”
你理解了 1、2、3、6，对 4、5 不清楚。
✅ “理解了 1、2、3、6。实现之前需要澄清第 4 和第 5 项。”
```

## GitHub 评论线程回复

在 GitHub 上回复行内评审评论时，要在评论线程内回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），而不是发成顶层 PR 评论。
