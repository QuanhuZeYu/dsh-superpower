# 运行时驱动开发

**主循环：运行目标程序 → 观察偏差 → 用探针区分假设 → 最小修改 → 同场景实机复测。**

这是与 `test-driven-development` 并列的反馈通道。两者都先跑通最小真实闭环，再根据反例和误差迭代；本模式以真实环境、日志和必要运行时断言取得反馈。不要求先写失败的自动化测试、不补造 RED，也不因没有先行测试而删除实现。

## 选择与边界

使用者指定模式时直接遵循，项目的明确约定也应保留；未指定时，稳定契约与纯逻辑适合 TDD，设备、UI、进程、网络和时序交互优先本模式。按任务选择，记录在简报中并传给实现者与评审者。模式发生变化时说明证据与原因，不为跳过失败而静默切换。

- `control-loop` 管目标、反馈与停止条件，`systematic-debugging` 管根因调查。本模式管实现和验证的顺序。
- 可以读代码定位入口、选择探针与审查改动；静态推理只产生假设。编译、类型检查、lint、mock 或离线模拟均不能代替目标环境的运行结果。
- “实机”指实际目标应用、进程或设备及相关依赖的运行实例；记录版本、配置、启动方式、访问地址或设备标识。确认修改已构建、部署到该实例并重新加载，不能拿旧进程或另开的无关实例验收。
- 新功能先运行最小纵向路径，观察它与目标的差距；缺陷修复先保留真实症状与输入。目标已经满足时如实记录，无须人为制造故障。

设计阶段先确定主路径、异常归属和下一步运行反馈；高层 spec 无需复制下面的执行记录模板。进入实现后再按具体场景取证，用户已有的阶段约定（例如架构稳定前不写测试代码）直接沿用。

## 1. 建立运行场景

明确谁执行什么操作、预期可见结果、必要边界，以及如何观察结果。记录当前版本和真实输入，运行原场景并保留原始日志、调用栈、工具反馈或操作记录。事实、用户报告和待验证假设分别标明。

尚无可运行实现时，先做满足该场景的最小实现并启动；不能只运行孤立断言来冒充应用运行。缺少设备、凭据或执行通道时，指出具体缺口；可继续准备探针，但实机结论保持“未验证”。

## 2. 布置并校验探针

每轮先写一句可证伪的问题，例如“完成通知是否早于写入完成？”，再在最少的关键边界增加探针：

- 用请求/会话标识串联入口、状态转换、跨组件调用和结果，按需记录输入摘要、状态前后值、错误与调用栈。时序问题使用同一时钟域的单调时间或明确的因果序号；不要直接比较不同设备的未同步时间。
- 主动触发一次目标路径，确认入口与结果均可见、日志级别及输出通道有效。没有日志可能是路径未命中、日志关闭或输出丢失；没有断言失败也可能是断言未执行。
- 只收集判断所需字段；避免输出凭据和完整敏感载荷。探针可开关、开销有界，不在高频路径无界打印。
- 日志、断点和断言会扰动时序；问题消失时对比探针开关与采样条件，保持症状“本次未复现”，不能据此判定修复。

## 3. 使用开发期运行时断言

允许在组件边界和状态转换检查已确认的不变量，让错误在靠近源头的位置暴露。触发时保留条件、实际值、关联标识和调用栈；再判断是业务缺陷、过强断言还是探针本身出错，不能把所有断言触发都算产品缺陷。

断言及其参数求值应无业务副作用，关闭后不得改变业务执行、数据或必要的资源清理。开发专用断言使用显式构建条件或开关；先检查项目断言机制是抛错、中断还是仅输出日志。需要抛错时使用可捕获的开发断言，不能假定 `console.assert` 会终止执行。

```ts
// 开发构建中检查内部契约；生产输入校验和错误处理另行保留。
if (DEV_DIAGNOSTICS && state === "saved" && !writeFinished) {
  throw new Error(`保存状态早于写入完成: requestId=${requestId}`);
}
```

上面只是代码示例，未执行过，不代表发现了错误。观测通道不确定时，可在隔离的开发实例中用已知违约输入验证断言能触发并保留实际输出；不得在真实用户环境人为制造故障。外部输入、网络/设备异常走正式校验与错误处理，不依赖可关闭的断言兜底。

## 4. 用反馈定位并修复

从实际输出找首次偏离目标的边界，列出少量竞争假设。每次改变一个相关因素或一处最小实现，用同一输入重跑，并记录什么现象支持或推翻假设。可以从日志追到代码，但不能仅凭“代码看起来有问题”声称已定位根因。

未复现时记录环境、输入和观察窗口，校准探针或选择能区分假设的下一个动作。反馈与预测不符时回到调查，不叠加猜测修复、不降低目标或删除断言掩盖错误。

修复后复跑原场景及相关边界；可将已明确、可稳定复现的行为沉淀为自动化回归。自动化不是本模式的前置门禁，也不能取代必要的实机验证。项目已有的必需检查仍要运行；构建失败就是构建失败，不能更名为验证成功。

## 5. 验收并收尾

完成预先约定的场景、必要重复与回归，无未解决失败即可停止。偶发问题要写清触发条件、尝试次数和观察窗口；一次没有出现故障只说明本次未复现。不要为了“防弹”无限运行，也不要把有限样本外推成普遍可靠。

逐项检查：

- 最终版本在目标实例运行，原场景的可见结果符合契约，关键边界有实际证据。修复前症状与修复后结果可比较；新功能没有旧症状时记录初始能力与最终验收即可。
- 核对原始反馈与目标路径；约定场景有缺口时继续执行验证，确需外部设备或访问时提出具体请求。
- 临时日志/断言移除或关闭；有长期诊断价值的可按项目约定保留，但默认状态、开销和用途明确。不要无条件删掉全部断言。
- 在最终交付配置（开发探针关闭或已移除）下再运行必要场景，确认行为不依赖断言求值、调试延迟或临时开关；保留正式校验和错误处理。

使用 `verification-before-completion` 核对结论，报告最小证据记录：

```text
开发模式：runtime-driven-development
目标与场景：实际输入/操作、预期可见结果、必要边界
运行实例：版本/构建、配置、启动方式、地址或设备标识
诊断：问题、探针与断言开关、目标路径命中依据
修复前/初始运行：原始记录位置、直接观察、未验证假设
最小改动：针对哪条证据，什么结果会推翻判断
修复后/最终运行：同场景操作、原始记录、实际结果与边界
交付配置复测：探针处理、断言状态、实际运行记录
结论：实际结果、验收情况及影响使用的剩余问题
```

命令输出、实际工具调用和有来源的实机操作记录均可作为反馈；只有转述时注明来源，不能写成自己亲自运行。按任务保留有用字段，已有日志直接引用。缺少必要反馈就运行对应场景；报告真实结果。
