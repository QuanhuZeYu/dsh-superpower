# 运行时驱动开发

**核心循环：运行目标实例 → 观察偏差 → 用探针/断言区分假设 → 最小修改 → 同场景及交付配置实机复测。**

本技能与 `test-driven-development` 并列：在真实环境、设备、UI、进程或时序交互起决定作用时，通过真实运行日志与开发期断言获取反馈。不要求先写自动化测试或补造 RED；静态代码阅读、编译或 lint 通过均不能替代目标实例的运行结果。

## 执行步骤

### 1. 建立实机场景与基线
明确操作步骤、预期可见结果与观察通道。确认改动已构建、部署并加载到**当前目标实例**（记录版本、配置、地址或设备标识，严禁拿旧进程或无关实例充数）。新功能先跑通最小纵向路径；修 bug 先复现并记录原始症状。缺少设备或凭据时标明具体缺口，结论保持“未验证”。

### 2. 布置探针与开发期断言
每轮围绕一个可证伪问题（如“完成通知是否早于落盘？”）在关键边界加最小探针：
- **关联与时钟：** 用请求/会话 ID 串联跨组件调用；时序问题使用同一时钟域的单调时间或因果序号。
- **确认触达：** 触发目标路径，确认探针实际输出（无日志可能是路径未命中或级别被过滤）。若加日志扰动了时序导致偶发问题消失，记为“本次未复现”，不直接判已修复。
- **开发期断言：** 在状态转换处用无业务副作用、受显式开关控制的断言检查内部不变量（如 `if (DEV_DIAGNOSTICS && !writeFinished) throw ...`）。外部输入与网络/设备异常仍走正式校验与错误处理。

### 3. 最小修改与收尾验收
每次只改一处相关实现，同输入重跑比对。修复后须完成：
1. **同场景与边界复测：** 目标实例可见结果符合契约，项目既有必需检查通过（可稳定自动化的部分按需沉淀回归）。
2. **交付配置复测：** 移除或关闭临时日志与开发断言后再次实测，确认行为不依赖调试延时或断言求值。

## 最小证据记录格式

使用 `verification-before-completion` 核对并报告关键证据（仅转述他人结果时须注明来源）：

```text
开发模式：runtime-driven-development
运行实例：<版本/构建、配置、地址或设备标识>
场景与诊断：<输入/操作、探针/断言开关及命中依据>
修复前/初始观察：<原始日志位置与实际现象>
修改与复测：<针对证据的最小改动 → 同场景复测结果 → 关闭临时诊断后的交付配置复测结果>
结论：<已验证范围及影响使用的剩余问题>
```
