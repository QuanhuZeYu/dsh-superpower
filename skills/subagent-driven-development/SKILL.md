# 子代理驱动开发

按任务逐个派发独立上下文的实现者子代理（`subagent`），每个任务完成后做一次规格符合性与代码质量评审，全部任务完成后做一次整分支宽口径评审。

**核心原则：** 独立子代理实现 + 逐任务双项评审 + 最终整分支评审 = 上下文干净、高质量快速收敛。工具调用之间最多叙述一行短句，进度与决定一律记入台账。

## 准备与恢复核对

1. **隔离工作区：** 用 `using-git-worktrees` 创建或核验隔离 worktree；未经明确同意，绝不在 `main/master` 上直接实现。
2. **定位计划工作区与台账：** 运行 `python scripts/sdd-workspace.py PLAN_FILE` 获取该计划专属目录（`<repo-root>/.superpowers/sdd/...`）。台账首行格式为 `# SDD 台账 — 计划：<计划文件路径>`，路径不符的旧台账绝不混用。
3. **恢复核对（上下文压缩或重入时）：** 比较计划/规格版本、任务文本与验收；确认已完成提交仍在当前历史且未被覆盖或破坏；核对当前工作树、依赖配置及原始验证证据的失效条件。记录 `恢复核对：<版本>；<验收>；<提交与工作树>；<证据及失效条件>；<沿用/重开及理由>`。仅跳过验收与证据仍有效的任务。
4. **预检扫描与建待办：** 通读计划与 Spec（Spec 为冲突裁决最高权威；无 Spec 时在台账注明裁决为临时）。扫描跨任务共享文件/接口及单任务内部自洽性，将冲突检查表与裁决（`裁决：<决定> — <证据与理由> — <影响与失效条件>`）写入台账，再用 `todo_write` 为所有任务建待办。

## 模型选择与开发模式传递

**派发 `subagent` 时永远显式指定 `model`**（省略会静默继承高成本主控模型）：
- **便宜模型：** 计划已含完整代码或单文件 1-2 处机械修改的实现者、小修复 diff 的范围受限复评审。
- **标准模型：** 涉及多文件协调、模式匹配或调试的实现者与常规任务评审。
- **最强模型：** 架构设计判断、最终整分支评审，或修复循环第 4-5 轮验证能力假设时。

**传递开发模式：** 简报必须指明 `test-driven-development` 或 `runtime-driven-development`（缺失时按 `using-superpowers` 选定并记台账）。两种模式都先跑通最小真实闭环再用反例/探针修正，不要求删除先写好的正确实现。

## 任务循环

同类多文件单行/常量小改动可合并为一份简报批量派发给单个子代理，绝不并行派发会冲突的实现子代理。等待后台子代理时，优先处理本地工作或按有界时间段等待并盘点（`list_agents`），不忙轮询。

### 1. 派发实现者（模板：[implementer-prompt.md](implementer-prompt.md)）
- 记录当前 `BASE = git rev-parse HEAD`。
- 运行 `python scripts/task-brief.py PLAN_FILE N` 生成任务简报（`.../task-N-brief.md`），约定报告路径为 `.../task-N-report.md`。
- 派发独立 `subagent`（不用 `subagent_fork`），仅传入：(1) 任务位置说明；(2) 简报路径（唯一需求来源，禁止让子代理读整份计划或粘贴往期历史）；(3) 前序任务产出的接口与相关台账裁决；(4) 报告路径与禁止派生子代理契约。记下返回的 `subagentId` 供修复轮恢复。

### 2. 处理实现者报告
- **DONE：** 运行 `python scripts/review-package.py PLAN_FILE BASE HEAD` 生成评审包文件（切勿用 `HEAD~1`，以免漏掉多提交任务的早期 commit），进入步骤 3。
- **DONE_WITH_CONCERNS：** 核对当前任务验收是否真正满足；存在正确性或验证缺口则视为未完成，仅不影响当前验收的观察项可记录后送审。
- **NEEDS_CONTEXT / BLOCKED：** 补充缺失上下文、裁决计划错误、拆分过大的任务或升级模型后重新派发；绝不原样强迫重试。

### 3. 逐任务评审（模板：[task-reviewer-prompt.md](task-reviewer-prompt.md)）
派发独立 `subagent`，传入**简报路径、报告路径、评审包路径**及逐字复制的 **Global Constraints**。
- 禁止让评审者重跑实现者已跑过的测试，也禁止在提示词中预先指示忽略某类问题。
- 对评审者报出的 `⚠️ 无法从 diff 验证` 条目，由主控结合跨任务上下文逐条核实；确属缺口则并入修复循环。

### 4. 修复循环与复评审（模板：[re-review-prompt.md](re-review-prompt.md)）
收到评审发现后，先凭代码路径与运行证据分诊：
- **证据排除的误报：** 任何轮次均可立即驳回，台账记录原发现、反证与适用版本。
- **与计划冲突：** 以 Spec 为权威做最小裁决并记台账。
- **不影响当前验收且无严重后果的 Minor：** 台账记为暂缓，不进修复轮。
- **真实缺口或 Critical / Important：** 进入修复轮（本轮投入预算默认 5 轮）。
  - **第 1-3 轮：** 用 `send_message` 恢复原实现者（附未决发现与新证据），按任务模式修复并追加报告。
  - **第 4-5 轮：** 重评需求、观测通道与方法假设，必要时换更强模型派发新实现者（次数本身不自动证明“架构错误”）。
  - **范围受限复评审：** 每轮修复后运行 `python scripts/review-package.py PLAN_FILE FIX_BASE HEAD`（`FIX_BASE` 为上轮评审 head），用 [re-review-prompt.md](re-review-prompt.md) 验证原发现与修复引入的新破坏；范围外发现若危及安全、数据完整性或当前验收，仍列为阻塞项。每轮记台账：`任务 <N>：修复轮次 <R>/5；已处理/误报已驳回/未决：<摘要>；commits <base>..<head>；下一步：<动作>`。

内部预算用尽仍未收敛时，重评并换实验、观测点或方法继续；仅用户/工具硬预算耗尽，或核实确缺外部输入、权限或资源时交接。验收未满足则保持未完成。

### 5. 完成任务
当任务验收满足、必需评审发现已解决或凭证据驳回、且验证证据对应当前版本时，记台账 `任务 <N>：完成（计划/规格版本 <版本>；commits <base>..<head>；验收 <结果>；evidence <路径>）` 并更新 `todo_write`。

## 最终评审与收尾

1. **最终整分支评审：** 运行 `python scripts/review-package.py PLAN_FILE MERGE_BASE HEAD`（如 `git merge-base main HEAD`），用最强模型派发 [code-reviewer.md](../requesting-code-review/code-reviewer.md)，同时指向台账中的暂缓项与裁决行。需修复项默认合并为一次修复派发 + 一次范围受限复评审；未满足整体验收前绝不转入交付。
2. **存档与汇总交付：**
   - 将台账中**全部** `裁决：` 行按顺序汇总到最终回复的「我作出的裁决」一节（附错了的代价）。
   - 将台账、报告与原始验证记录存档到不随临时工作区或 worktree 删除的持久位置，核对链接可达后，再删除本计划的 `.superpowers/sdd/<plan>` 临时目录（勿动同级其它计划目录）。
   - 加载 `finishing-a-development-branch` 技能收尾。

## 常见误区对照

| 借口 | 实际规则 |
| --- | --- |
| “修复很小，我自己顺手改了 / 跳过复评审” | 主控亲改会污染上下文且绕过门禁；恢复实现者，并用范围受限复评审收尾。 |
| “台账记账太啰嗦，过几个任务再补” | 上下文压缩随时发生；无台账会导致主控重复派发已完成的任务序列。 |
| “实现者自己派了评审者，多一层保障” | 那是全额成本的重复席位；实现者严禁派生任何子代理。 |
