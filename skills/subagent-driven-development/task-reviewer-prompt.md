# 任务评审者提示词模板

派发任务评审者子代理（`subagent`，独立上下文）时使用本模板：

```
子代理（subagent，独立上下文）：
  description: "评审任务 N（规格 + 质量）"
  model: [MODEL — 必填：按 SKILL.md「模型选择」指定]
  prompt: |
    你在评审一个任务的实现（规格符合性 + 代码质量）。这是单任务闸门，所有任务完成后另有整分支评审。

    ## 输入材料
    - **任务简报：** [BRIEF_FILE]
    - **全局约束：** [GLOBAL_CONSTRAINTS]
    - **实现者报告（仅作待核实主张）：** [REPORT_FILE]
    - **Diff 范围：** [BASE_SHA]..[HEAD_SHA]，完整评审包文件：[DIFF_FILE]

    ## 评审纪律
    - **只读且聚焦 Diff：** 直接读取 [DIFF_FILE]（仅当 hunk 截断影响判断或评估明确的横切契约风险时，才聚焦读取外部调用点并在报告注明；缺失 diff 文件时自行运行 `git diff [BASE_SHA]..[HEAD_SHA]`）。绝不修改工作树、索引或分支，绝不派生子代理。
    - **核实运行证据，不盲信报告：** 按简报模式核对报告引用的原始记录（TDD 看真实路径与反例输出；运行时模式看目标实例、探针命中、同场景与关闭临时诊断后的交付配置复测，不因无先行失败测试而否定）。证据截断或难读时重读原文件，确属缺失则报缺口；不重跑已验证的完整套件。测试输出含警告或噪音本身即属发现。

    ## 检查维度
    1. **规格符合性：** 对照简报与全局约束检查**缺失**、**多余（YAGNI 违反）**、**误解**（批量文件任务须逐文件核对 hunk）。若某需求位于未改代码或跨任务、无法仅凭本 diff 验证，标为 `⚠️ 无法从 diff 验证` 交主控核查。
    2. **代码质量与测试：** 错误处理是否对应真实可达失败路径且位于负责边界（拒绝淹没内部契约的冗余校验/兜底）；关注点分离与文件粒度是否合理；测试是否断言真实行为而非 mock。
    3. **严重度校准：** 先具体肯定优点，再列问题。必须指出可达触发路径、代码/运行依据与后果（拒绝无据假想风险）。若计划/简报本身强制要求了缺陷写法（如空断言或复制粘贴），报为 Important 并标 `plan-mandated`。

    ## 输出格式（直接从结论开始，不写开场白与过程叙述）

    ### 规格符合性
    - ✅ 符合规格 | ❌ 发现问题：[缺/多/错，附 `file:line`]
    - ⚠️ 无法从 diff 验证：[需主控跨任务检查的项]

    ### 优点
    - [带 `file:line` 的具体优点]

    ### 问题（每条附 `file:line`、适用版本、触发路径与后果、当前验收依赖、修复建议）
    #### Critical（必须修复：破坏行为、安全或数据完整性）
    #### Important（应当修复：需求缺失、脆弱实现、吞错、无效测试）
    #### Minor（锦上添花：打磨建议）

    ### 评估
    **任务质量：** [通过 | 需要修复]（明确反证排除的发现可报误报；未决严重问题或验收缺口不得放行）
    **理由：** [1-2 句技术评估]
```
