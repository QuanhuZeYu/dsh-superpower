# 系统化调试

## 概述

**核心原则：** 通过观察与可控实验定位原因，再用真实结果验证修复。

先读取已有报错和相关路径，提出可检验假设，做最小实验。实验可以包含局部可逆修改；结果不符预期时更新假设继续。根因尚未确定不妨碍调查性动作，最终修复则需解释并消除目标症状。

## 使用时机

适用于任何技术问题：
- 测试失败
- 生产环境的 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要使用：**
- 面临时间压力时（紧急状况会让猜测变得诱人）
- "就一个小修复"看起来显而易见时
- 你已经试过多个修复时
- 上一个修复没有奏效时
- 你还没有完全理解问题时

**以下情况不要跳过：**
- 问题看起来很简单（简单 bug 也有根因）
- 你在赶时间（赶工必然带来返工）
- 主管要求现在就修好（系统化比乱撞更快）

## 开发模式

按 `using-superpowers` 选择 TDD 或 `runtime-driven-development`。以下根因调查对两者都适用；运行时模式从真实日志、开发期断言和实机行为提出并验证假设，代码阅读辅助布置探针。阶段 4 按所选模式取得证据，不能把静态推理当成已复现的根因。

## 四个阶段

按当前缺口选择阶段：已有证据可直接用于假设和实验；新反馈改变判断时只补受影响的调查。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读报错信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整读完调用栈
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的复现步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查最近的改动**
   - 改了什么可能导致这个问题？
   - Git diff、最近的 commit
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，先加上诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   先跑一次，收集"坏在哪一层"的证据
   然后分析证据，定位出错的组件
   再深入调查那个具体组件
   ```

   **示例（多层系统）：**
   ```python
   import os
   import subprocess

   # 第 1 层：workflow
   print("=== workflow 中可用的 secrets ===")
   identity = os.environ.get("IDENTITY")
   print("IDENTITY:", "SET" if identity else "UNSET")

   # 第 2 层：构建脚本
   print("=== 构建脚本中的环境变量 ===")
   matches = [f"{k}={v}" for k, v in os.environ.items() if "IDENTITY" in k]
   print("\n".join(matches) if matches else "IDENTITY 不在环境变量里")

   # 第 3 层：签名脚本
   print("=== keychain 状态 ===")
   subprocess.run(["security", "list-keychains"])
   subprocess.run(["security", "find-identity", "-v"])

   # 第 4 层：实际签名
   subprocess.run(["codesign", "--sign", identity, "--verbose=4", app])
   ```

   **这揭示了：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈里：**

   完整的前向回溯技术见本目录的 `root-cause-tracing.md`。

   **速览版：**
   - 坏值是从哪里产生的？
   - 谁带着坏值调用了这里？
   - 一路向上追，直到找到源头
   - 在源头修复，而不是在症状处修

### 阶段 2：模式分析

**先找模式，再动手修：**

1. **找到可用的范例**
   - 在同一个代码库里找出类似的、能正常工作的代码
   - 有哪些能正常工作的东西和坏掉的东西相似？

2. **与参照实现对比**
   - 如果要实现某个模式，就完整地读参考实现
   - 不要略读 —— 逐行读
   - 完全理解这个模式之后再套用

3. **找出差异**
   - 能工作的和坏掉的之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖**
   - 它还需要哪些其它组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **只提出单个假设**
   - 明确表述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 用尽可能小的改动来验证假设
   - 一次只动一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 成功了吗？是 → 阶段 4
   - 没成功？提出新的假设
   - 不要在原有基础上继续叠加修复

4. **当你不知道时**
   - 把未知缩成一个能回答的问题，定位相关代码、输入或日志
   - 运行一个能区分可能原因的小实验，按结果继续
   - 确认必须由外部提供的信息或访问后，提出具体请求

### 阶段 4：实施

**修根因，不修症状：**

1. **保留修复前的行为证据**
   - TDD：用 `test-driven-development` 建立调用真实路径的失败测试
   - 运行时模式：用 `runtime-driven-development` 记录实机复现步骤、实例版本与原始日志/断言/操作反馈；不要求先写自动化测试
   - 确认目标路径实际触达；未复现就补观测，不制造失败
   - 能稳定自动化的场景可沉淀为回归，但不把它作为运行时模式的先行门禁

2. **实施单一修复**
   - 针对已经定位的根因
   - 一次只改一处
   - 不要"顺手"做改进
   - 不要夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 有没有弄坏其它测试？
   - 问题真的解决了吗？
   - 声称成功之前，先用 `verification-before-completion` 技能

4. **如果修复无效：利用失败推进**
   - 读取实际结果，确定原假设被支持、被排除还是观测不足。
   - 跑错产物、未命中路径或环境变化时，修复反馈通道并复测。
   - 否定一个假设后，选择能区分剩余原因的最小实验并执行；不必先证明新假设正确。
   - 相同尝试不再提供信息时换方法。内部轮次用于重选策略，硬资源限制按实际授权处理。

5. **依据证据选择下一种策略**
   - 发现旧产物或探针失效：先修复反馈通道，再复测原场景。
   - 有证据支持局部根因：在授权范围内最小修复并验证。
   - 持续出现共享状态耦合、局部修复引发跨边界症状等证据：把架构问题列为假设，用最小实验验证；涉及范围或必要设计决定时与使用者讨论。
   - 缺必要输入、权限或能力：先核查现有通道；确需外部提供时提出具体请求，其余工作继续。

失败次数是重评信号，不能单独证明架构错误，也不自动要求更换模型或扩大改动。

## 区分实验与盲目改动

可逆尝试允许失败。先确定要区分的假设、观察结果和影响边界，再执行；无需等待完全理解系统。下面这些行为会丢失反馈价值，应改成单一实验：
- "先快速修一下，之后再调查"
- 改 X 却未确定要观察什么，结果无论成败都无法更新判断
- "一次加多个改动，跑测试看看"
- "跳过所选开发模式要求的验证"
- "大概是 X 的问题，我把它修了"
- 把尚待检验的猜想直接当作已确定的修复结论
- "主要问题有这些：[没做调查就列出修复清单]"
- 还没追踪数据流就提出解决方案
- **没有新证据却继续重复同一种修复**
- **每个修复都在不同的地方暴露出新问题**

**保留已取得的有效信息，只补当前缺口，然后执行下一步。** 不必因一次失败从头重走调查。

**预算耗尽或反复无进展：** 检查反馈通道与假设，按阶段 4.5 选择下一步。

## 使用者给出的"你做错了"信号

**留意这些纠正：**
- "那个真的发生了吗？" —— 你没验证就做了假设
- "它会告诉我们……吗？" —— 你本该加上证据收集
- "别猜了" —— 你在还没理解时就提出修复方案
- "深入思考一下" —— 要质疑根本假设，而不只是症状
- "我们卡住了？"（带着挫败） —— 你的做法不奏效

**看到这些时：** 找到具体缺失的观测，用工具补齐并更新下一步。

## 常见的自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 bug 来说流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜来猜去的乱撞更快。 |
| "先试一下，然后再调查" | 明确假设、观察点与可控范围后即可做实验；用结果决定是否保留改动。 |
| "等交付后再验证" | 两种模式都需要运行证据：TDD 看有效 RED→GREEN，运行时模式看实机症状、同场景复测和交付配置验证。 |
| "一次改多个修复更省时间" | 无法定位哪个起了作用。还会引入新 bug。 |
| "参考实现太长，我照着模式改改就行" | 读取影响当前契约的部分，用最小运行验证理解；发现缺口再扩大阅读。 |
| "我看到问题了，我来修" | 看到症状 ≠ 理解根因。 |
| "没有新证据，再修一次试试" | 停止原样重试，检查反馈通道，换一个能区分原因的观测。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读报错、复现、检查改动、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找可用的范例、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小化验证 | 假设被证实，或产生新假设 |
| **4. 实施** | 按所选模式保留症状、最小修复、同场景验证 | 实际行为满足契约，必要检查通过 |

## 当流程表明"没有根因"时

如果系统化的调查表明问题确实是环境性的、时序相关的或外部引起的：

1. 你已经走完了流程
2. 记录你调查了什么
3. 实施恰当的处理（重试、超时、错误提示）
4. 为后续调查加上监控/日志

尚未定位根因时保留未知状态；已有证据指向环境或外部因素时，按对应路径验证，不用固定比例替代判断。

## 支撑技术

这些技术是系统化调试的一部分，就在本目录中：

- **`root-cause-tracing.md`** —— 沿着调用栈向后追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** —— 修复根因后按真实失败路径放置必要防护，复用已有边界处理
- **`condition-based-waiting.md`** —— 用条件轮询替代任意的超时
