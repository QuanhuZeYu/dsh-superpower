# 系统化调试

## 概述

**核心原则：** 永远先找到根因，再尝试修复。只修症状就是失败。

**违反本流程的字面要求，就是违反调试的精神。**

## 铁律

```
不先做根因调查，不许动手修复
```

如果你没有完成阶段 1，就不能提出修复方案。

## 使用时机

适用于任何技术问题：
- 测试失败
- 生产环境的 bug
- 异常行为
- 性能问题
- 构建失败
- 集成问题

**以下情况尤其要使用：**
- 面临时间压力时（紧急状况会让猜测变得诱人）
- "就一个小修复"看起来显而易见时
- 你已经试过多个修复时
- 上一个修复没有奏效时
- 你还没有完全理解问题时

**以下情况不要跳过：**
- 问题看起来很简单（简单 bug 也有根因）
- 你在赶时间（赶工必然带来返工）
- 主管要求现在就修好（系统化比乱撞更快）

## 四个阶段

你必须完成每个阶段，才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读报错信息**
   - 不要跳过错误或警告
   - 它们往往包含确切的解决方案
   - 完整读完调用栈
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 确切的复现步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜

3. **检查最近的改动**
   - 改了什么可能导致这个问题？
   - Git diff、最近的 commit
   - 新增依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统包含多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，先加上诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传递
     - 检查每一层的状态

   先跑一次，收集"坏在哪一层"的证据
   然后分析证据，定位出错的组件
   再深入调查那个具体组件
   ```

   **示例（多层系统）：**
   ```python
   import os
   import subprocess

   # 第 1 层：workflow
   print("=== workflow 中可用的 secrets ===")
   identity = os.environ.get("IDENTITY")
   print("IDENTITY:", "SET" if identity else "UNSET")

   # 第 2 层：构建脚本
   print("=== 构建脚本中的环境变量 ===")
   matches = [f"{k}={v}" for k, v in os.environ.items() if "IDENTITY" in k]
   print("\n".join(matches) if matches else "IDENTITY 不在环境变量里")

   # 第 3 层：签名脚本
   print("=== keychain 状态 ===")
   subprocess.run(["security", "list-keychains"])
   subprocess.run(["security", "find-identity", "-v"])

   # 第 4 层：实际签名
   subprocess.run(["codesign", "--sign", identity, "--verbose=4", app])
   ```

   **这揭示了：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误深藏在调用栈里：**

   完整的前向回溯技术见本目录的 `root-cause-tracing.md`。

   **速览版：**
   - 坏值是从哪里产生的？
   - 谁带着坏值调用了这里？
   - 一路向上追，直到找到源头
   - 在源头修复，而不是在症状处修

### 阶段 2：模式分析

**先找模式，再动手修：**

1. **找到可用的范例**
   - 在同一个代码库里找出类似的、能正常工作的代码
   - 有哪些能正常工作的东西和坏掉的东西相似？

2. **与参照实现对比**
   - 如果要实现某个模式，就完整地读参考实现
   - 不要略读 —— 逐行读
   - 完全理解这个模式之后再套用

3. **找出差异**
   - 能工作的和坏掉的之间有什么不同？
   - 列出每一处差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖**
   - 它还需要哪些其它组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **只提出单个假设**
   - 明确表述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 用尽可能小的改动来验证假设
   - 一次只动一个变量
   - 不要一次修多个东西

3. **继续之前先验证**
   - 成功了吗？是 → 阶段 4
   - 没成功？提出新的假设
   - 不要在原有基础上继续叠加修复

4. **当你不知道时**
   - 说出"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多调研

### 阶段 4：实施

**修根因，不修症状：**

1. **创建失败测试用例**
   - 尽可能最简单的复现
   - 能自动化就自动化
   - 没有测试框架就写一次性测试脚本
   - 修复之前必须先有它
   - 用 `test-driven-development` 技能来写规范的失败测试

2. **实施单一修复**
   - 针对已经定位的根因
   - 一次只改一处
   - 不要"顺手"做改进
   - 不要夹带重构

3. **验证修复**
   - 测试现在通过了吗？
   - 有没有弄坏其它测试？
   - 问题真的解决了吗？
   - 声称成功之前，先用 `verification-before-completion` 技能

4. **如果修复无效**
   - 停下来
   - 数一数：你已经试过几个修复？
   - 如果 < 3：回到阶段 1，带着新信息重新分析
   - **如果 ≥ 3：停下来质疑架构（见下面第 5 步）**
   - 没有架构层面的讨论，不要尝试第 4 个修复

5. **如果 3 个以上修复都失败：质疑架构**

   **表明架构有问题的模式：**
   - 每个修复都在不同的地方暴露出新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能落地
   - 每个修复都会在别处制造新症状

   **停下来，质疑根本假设：**
   - 这个模式从根本上站得住脚吗？
   - 我们是不是"纯靠惯性在硬撑"？
   - 该重构架构，还是继续修症状？

   **在尝试更多修复之前，先和使用者讨论**

   这不是假设失败 —— 这是架构错了。

## 危险信号 —— 停下来走流程

如果发现自己有这些想法：
- "先快速修一下，之后再调查"
- "就试着改改 X，看能不能好"
- "一次加多个改动，跑测试看看"
- "跳过测试，我手动验证"
- "大概是 X 的问题，我把它修了"
- "我没有完全理解，但这样可能行"
- "模式里写的是 X，但我换个方式改"
- "主要问题有这些：[没做调查就列出修复清单]"
- 还没追踪数据流就提出解决方案
- **"再修一次试试"（已经试过 2 次以上时）**
- **每个修复都在不同的地方暴露出新问题**

**以上所有情况都意味着：停下来。回到阶段 1。**

**如果 3 个以上修复失败：** 质疑架构（见阶段 4.5）

## 使用者给出的"你做错了"信号

**留意这些纠正：**
- "那个真的发生了吗？" —— 你没验证就做了假设
- "它会告诉我们……吗？" —— 你本该加上证据收集
- "别猜了" —— 你在还没理解时就提出修复方案
- "深入思考一下" —— 要质疑根本假设，而不只是症状
- "我们卡住了？"（带着挫败） —— 你的做法不奏效

**看到这些时：** 停下来。回到阶段 1。

## 常见的自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题很简单，不需要流程" | 简单问题也有根因。对简单 bug 来说流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜来猜去的乱撞更快。 |
| "先试一下，然后再调查" | 第一个修复会定下基调。从一开始就做对。 |
| "等确认修复有效后我再写测试" | 没测过的修复站不住脚。先写测试才能证明。 |
| "一次改多个修复更省时间" | 无法定位哪个起了作用。还会引入新 bug。 |
| "参考实现太长，我照着模式改改就行" | 理解不完整必然带来 bug。完整读完。 |
| "我看到问题了，我来修" | 看到症状 ≠ 理解根因。 |
| "再修一次试试"（失败 2 次以上之后） | 3 次以上失败 = 架构问题。质疑模式，别再修了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读报错、复现、检查改动、收集证据 | 理解 WHAT 和 WHY |
| **2. 模式** | 找可用的范例、对比 | 找出差异 |
| **3. 假设** | 形成理论、最小化验证 | 假设被证实，或产生新假设 |
| **4. 实施** | 写测试、修复、验证 | bug 解决，测试通过 |

## 当流程表明"没有根因"时

如果系统化的调查表明问题确实是环境性的、时序相关的或外部引起的：

1. 你已经走完了流程
2. 记录你调查了什么
3. 实施恰当的处理（重试、超时、错误提示）
4. 为后续调查加上监控/日志

**但是：** 95% 的"没有根因"都是调查不完整。

## 支撑技术

这些技术是系统化调试的一部分，就在本目录中：

- **`root-cause-tracing.md`** —— 沿着调用栈向后追踪 bug，找到最初的触发点
- **`defense-in-depth.md`** —— 找到根因后，在多个层加上校验
- **`condition-based-waiting.md`** —— 用条件轮询替代任意的超时
