# 系统化调试

**核心原则：** 通过观察与可控实验定位根因，再用真实结果验证修复。

先读取报错与相关路径，提出可检验假设，执行最小可逆实验；结果不符预期时更新假设。根因未定不影响做调查性实验，但最终修复必须解释并消除目标症状。

## 使用时机

适用于测试失败、生产 bug、异常行为、性能退化、构建或集成失败。**尤其在时间紧迫、看似“顺手小修”、或已尝试多次修复未果时，绝不跳过。**

按 `using-superpowers` 选择 `test-driven-development` 或 `runtime-driven-development`：代码阅读只用于提出假设和布置探针，不能替代真实运行证据。

## 四个阶段

按当前信息缺口切入；已有有效证据直接复用，失败后只补当前缺口。

| 阶段 | 关键动作 | 成功标准 |
| --- | --- | --- |
| **1. 根因调查** | 读报错、稳定复现、查近期改动、跨组件埋点、追踪数据流 | 明确坏在哪里（WHAT）及为何出错（WHY） |
| **2. 模式分析** | 查找代码库内正常工作的同类实现，逐处对比配置、输入与依赖 | 列出正常路径与故障路径的关键差异 |
| **3. 假设与验证** | 提出单一具体假设（“X 导致问题，因为 Y”），一次只改一个变量做最小实验 | 假设被证实，或凭结果排除并提出新假设 |
| **4. 实施修复** | 按开发模式保留故障证据，针对源头做单一修复，同场景验证并回归 | 原症状消失，契约满足，无新增破坏 |

### 阶段 1：根因调查要点

1. **完整读报错与调用栈：** 记录文件路径、行号、错误码，不略过警告。
2. **稳定复现与查改动：** 明确触发步骤与条件，检查近期 `git diff`、依赖与环境变更。无法复现时先加观测，不盲猜。
3. **多组件边界埋点：** 涉及多层调用（如 `workflow → 构建脚本 → 签名/服务`）时，在组件边界打印输入、输出与环境变量，先跑一次定位坏在哪一层：
   ```python
   import os

   # 在边界记录关键状态存在性（避免泄露敏感值）
   print(" Layer 1 IDENTITY:", "SET" if os.environ.get("IDENTITY") else "UNSET")
   ```
4. **追踪数据流源头：** 当坏值出现在调用栈深处时，沿调用链向上追溯最初的产生点（详见 `root-cause-tracing.md`），在源头修复而非症状处兜底。

### 阶段 2 & 3：对比模式与单变量实验

- **对比参照实现：** 找到同库正常工作的相似代码，完整阅读并对比输入、初始化顺序、环境假设。
- **区分实验与盲目改动：** 实验必须预先明确要验证的假设、观察指标与可逆范围。禁止“一次改多处跑跑看”、禁止无新证据重复同一种修复、禁止把未验证猜想当结论。

### 阶段 4：实施与失败推进

1. **保留修复前证据：** TDD 模式复用真实运行并补必要反例；运行时模式记录实例版本、复现步骤与原始日志/断言反馈。确认目标路径实际触达。
2. **单一根因修复：** 只改定位到的根因，不夹带重构或顺手优化；必要边界防护见 `defense-in-depth.md`。
3. **验证与失败分诊：** 使用 `verification-before-completion` 核验。若修复无效：
   - 跑错实例或未命中路径 → 先修复观测通道再复测。
   - 假设被推翻 → 依据新结果换能区分剩余原因的最小实验。
   - 局部修复不断在别处引发新症状、暴露共享状态耦合 → 将架构问题列为假设验证，涉及重大变更时与使用者讨论。
   - 证实属于外部环境或时序偶发 → 记录调查证据，实施重试/超时/明确报错并补充监控日志。

## 常见误区对照

| 常见借口 | 实际处理 |
| --- | --- |
| “问题很简单 / 时间紧，先修再说” | 简单 bug 走流程同样最快；盲目乱撞比先看清根因更耗时。 |
| “一次改多个地方省时间” | 无法判断哪个改动生效，且极易引入新 bug。一次只动一个变量。 |
| “我看到报错位置了，直接加个判空” | 看到症状 ≠ 理解根因；先向上追出非法值的源头。 |
| “没有新证据，再试一次也许能过” | 停止原样重试，检查反馈通道，换一个能区分原因的观测点。 |

## 同目录支撑技术

- `root-cause-tracing.md` —— 沿调用栈逆向追踪坏值源头及污染测试定位（配 `find-polluter.py`）
- `defense-in-depth.md` —— 修复根因后按独立失败边界放置必要防护
- `condition-based-waiting.md` —— 用条件轮询（配 `condition-based-waiting-example.ts`）替代脆弱的固定延时
