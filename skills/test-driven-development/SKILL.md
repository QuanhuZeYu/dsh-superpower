# 以真实闭环与反例推进开发（TDD）

**核心原则：** 先跑通最小真实闭环，再举反例围堵；由实际误差驱动修改，满足验收即停。

保留技能名供发现；开发顺序以本文件为准。不要求测试先于实现编写，也不把“曾经失败（RED）”当作有效性的前提。已跑通且正确的最小实现直接保留，禁止因测试晚写而删除或重写。

## 默认推进顺序

1. **定可观察目标：** 明确输入、预期输出与边界；沿用已有任务约定与运行入口。
2. **跑通最小真实路径：** 编写或复用最少实现，用真实输入跑通并观察结果。修复已知缺陷时直接从现有症状切入。
3. **举有依据的反例：** 从合同约束、调用边界和真实故障中选少量能推翻当前实现的反例（空值、重复、越界、状态切换等），不展开通用穷举清单。
4. **独立期望与误差修正：** 期望值必须源自合同或独立字面量，禁止用被测代码自己算期望。反例失败则修根因；反例直接通过则核对路径后如实记录，不破坏实现凑失败记录。
5. **回归与交付：** 重跑受影响路径、反例与项目必需检查。仅沉淀能防住具体回归或替代实机验证的测试，达标即收尾。

## 测试质量与验证边界

具体编写判据见 [writing-good-tests.md](writing-good-tests.md)，核心准则：

- **测消费者可见行为：** 优先真实集成入口，不镜像私有实现、源码文本或调用顺序；不为测试给生产代码加专用方法。
- **克制使用替身（Mock）：** 仅替掉昂贵或不可用的外部边界，并注明其限制；禁止 mock 本次要验证的核心行为，也禁止对 mock 本身下断言。
- **区分目标、预测与观测：** 只有真实运行输出才是观测证据。仅当观测通道本身存疑时，才用已知反例或隔离扰动校验通道。

## 常见偏差修正

| 观测到的偏差 | 下一步动作 |
| --- | --- |
| 主路径未跑通就先堆边界接口与抽象 | 缩回一条最小真实闭环，先拿到运行反馈 |
| 测试晚于实现完成 | 保留正确实现，直接补跑必要反例并记录结果 |
| 运行失败源于入口、编译或环境缺失 | 先修复观测通道，不将其算作业务反例失败 |
| 测试只断言 mock 或复写生产逻辑 | 改为断言真实消费者结果，或删掉无价值测试 |
