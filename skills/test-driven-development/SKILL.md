# 以真实闭环与反例推进开发（TDD）

## 核心原则

**先跑通最小真实闭环，再举反例围堵；由实际误差驱动修改，满足验收后停止。**

保留现有技能名供调用方发现。开发顺序以本文件为准，不要求测试写在实现之前，也不把“曾经失败”当作实现或测试有效的必要条件。正确且已运行的最小实现可以直接保留；不得因为测试晚写而删除、撤销或重写它。

本技能与 `runtime-driven-development` 共用控制论闭环：观测 → 判断误差 → 最小动作 → 反馈 → 修正。这里优先采用自动运行、契约与集成场景；设备和真实环境决定行为时采用对应运行通道。模式区别在反馈来源，不在实现先后顺序。

## 默认推进顺序

1. **定一个可观察目标。** 谁在什么输入下得到什么结果？复用现有流程、依赖与运行入口，说明本次边界。已有任务约定直接沿用，不重复设计和授权。
2. **先跑通一条最小真实路径。** 写或调整最少实现，用真实输入运行，观察输出、副作用或资源变化。已有闭环直接复用；已知故障从现有症状定位和修正，无需先制造一个成功或失败阶段。临时实验是否保留，由其是否正确、必要且符合架构决定，不按编写顺序删除。
3. **举有依据的反例。** 从需求约束、调用边界、真实故障和代码评审中选择能推翻当前结论的输入。围堵重复、空值、边界、状态切换、并发或清理等实际相关路径，不能把通用清单全展开为本轮任务。
4. **运行反例并修正误差。** 期望来自用户合同或独立数据，不能用被测实现生成自己的答案。反例失败时核对目标路径和原因，只修对应根因；反例通过就是本次已验证，不必破坏实现凑失败记录。
5. **回归并交付。** 重跑受修改影响的原路径与反例，执行项目必需检查。能防住具体回归或替代实机验证的测试才沉淀；达到约定验收后停止扩展。

反例可以在首次运行之前就被发现；已有缺陷的失败记录也可以直接使用。上面的顺序用于避免未跑通就围绕假设堆设计，不是新的阶段仪式。多个步骤可在同一次实际运行中完成。

## 验证投入

- 优先现有集成入口和真实生产路径。只为缩小已知问题或取得必要反馈添加测试，不按每个函数、字段或分支机械建测试。
- 外部边界确实昂贵或不可用时使用必要替身，说明它限制了什么结论；不得 mock 掉本次要验证的行为。
- 测试描述消费者可观察结果，不镜像私有实现、源码文字或调用顺序。实现重构而合同未变时，测试不应乱报警。
- 不为猜测中的反例预建通用框架、配置、缓存、重试或兼容层。发现真实误差后再选最小机制，先复用项目已有抽象。
- 普通可逆选择由代理完成；已授权范围内不为测试顺序、临时文件或保留正确实现重复申请豁免。必要的目标、合同或权限缺口才暂停对应步骤。

编写测试的具体判据见 [writing-good-tests.md](writing-good-tests.md)，按需读取，不把参考清单升级为一套强制流程。

## 证据与结论

**目标、预测、观测分开。** 需求和 expected 值表达目标；推演用于选反例；真实命令、调用或工具返回才是观测。测试代码存在、编译成功或写了断言，都不等于行为验证通过。

记录足够复核的信息：当前版本与输入、运行入口、原始结果、实际覆盖及限制。复用已有日志，不为每个步骤创建重复报告。结论只覆盖实际运行路径，自动注入事件不能称作完整原生设备链实测。

一次测试直接通过可以证明其实际输入的结果；它是否能捕获目标缺陷，还需核对独立期望与路径。只有这个反馈通道存在疑问时，才用已知反例、独立对照或隔离扰动校验它。不得为了获得 RED 而修改用户环境、破坏正确实现或无条件回退。

RED/GREEN 可以描述真实失败/通过，不能作为必须凑齐的流程凭证。没有运行就写未验证；结果未满足目标就继续修正，不能为了收尾降低标准。

## 一个通用例子

任务：按有效上限接受申请，不能重复占用名额。

先让“有效申请 → 返回结果 → 消费者看到名额变化”在真实入口跑通。再依据合同运行少量反例：达到上限后再申请、同一请求重复递交、释放后再次申请。若重复递交错误地多占名额，就定位身份处理并最小修正，再运行原成功路径和这些反例。

测试可以在实现跑通后加入并立即通过。若已有重复申请故障日志，则直接从该事实定位，不重做正常路径、删除实现或另造先行失败脚手架。

## 常见偏差与下一步

| 观测 | 下一步 |
| --- | --- |
| 主路径还没跑通，就不断增加边界接口与假设 | 缩回一条真实闭环，先取得反馈 |
| 反例暴露了合同错误 | 保留原始结果，修根因，回归受影响路径 |
| 反例直接通过 | 核对独立期望和路径，记录通过，继续必要验收 |
| 测试晚于实现 | 保留正确实现；补必要反例，无需撤销重写 |
| 运行失败来自入口、依赖或编译 | 修观测通道，不能把它称作行为反例 |
| 测试重复实现或只检查 mock | 改为真实消费者结果，或删除无价值断言 |
| 验收已满足，却继续穷举和抽象 | 收尾，不为流程完整性继续扰动 |

**退出条件：** 最小真实路径可用，必要反例和项目约定检查通过，关键反馈收齐。交付实际结果、边界与未验证项，不宣称不存在任何未知问题。
