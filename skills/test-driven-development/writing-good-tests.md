# 编写好测试

**在以下情况加载这份参考：** 编写或修改测试、添加 mock，或为测试添加清理/辅助方法。

## 概述

一个测试的存在，是为了抓住某一处特定的破坏。下面两条原则统辖这里的一切：

```
1. 每个测试都点明它能抓住的那处破坏
2. 每个测试都跑真实的东西
```

严格的 TDD 会自然产生这两者：先写、并对着真实代码看着它失败的测试，已经证明了它会失败；只有当真实依赖被证明很慢或位于外部时，测试才有资格使用 mock。

## 原则 1：点明那处破坏

在写测试正文之前，先回答：**什么样的生产代码改动会让这个测试失败 —— 而那处改动是一个 bug，还是一个决定？** 一个测试靠抓住错误分支、缺失的副作用、错误的参数、边界情况或违反的契约，来赢得它的位置。

**独立推导期望值。** 使用字面量和人工核对的 fixture；带字面量 `want` 值的表驱动测试是首选形态。由被测代码 —— 或它的辅助函数 —— 算出来的期望值，无论那段代码做什么都会通过：

```typescript
// ❌ 镜像断言：同一个 builder 算出了两边 —— 永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要变更探测器。** 如果只有刻意的决定才能让测试失败 —— 某个常量的值、消息的确切措辞、私有结构 —— 那它对重构乱报警，对 bug 却睡大觉。去测依赖该决定的行为：不是 `expect(MAX_RETRIES).toBe(5)`，而是"一次失败的调用会被重试 5 次，第 6 次尝试永远不会发生"。

**测行为，不测文本。** 断言某个脚本、技能或配置里含有某一行原文，只能证明源码就是源码。用受控输入运行脚本，断言输出、副作用或退出码。指导代理的文档，由消费它的代理的行为来检验（见 `writing-skills` 技能）；写给人类看的散文根本不值得写测试。

**测你的代码，不测框架。** 测你的代码在边界上做出的契约 —— 你注册的路由、你发出的查询、你产出的载荷。上游机制是它们的维护者该写的测试（经典例子：断言你的路由器调用了已注册的处理器 —— 那是框架的测试，不是你的）。当上游行为确实让你意外时，写一个范围很窄的特征测试，把那个假设点明。同一条边界在代码内部同样适用：构造函数、getter、常量、纯转发只有在做校验、归一化、设默认值、推导、强制约束或产生副作用时，才配拥有测试 —— 否则就去断言第一个依赖它们的、消费者可见的结果。

### 把关函数

```
在写测试正文之前：
  点明会让这个测试失败的那处生产代码改动。

  点不出来                    → 围绕某个可观察行为重新设计
  "源码文本变了"              → 运行产物并断言它的效果
  只有刻意的决定能让它失败     → 变更探测器；去测依赖该决定的行为

  确认期望值不是用被测代码推导出来的。
  如果它复用了被测代码的逻辑或辅助函数：
    换成字面量或人工核对的 fixture
```

## 原则 2：跑真实的东西

**mock 不配被断言。** 对 mock 的断言，mock 在场就通过、缺席就失败 —— 它对组件本身什么也没说。断言真实组件的行为；如果你检查的其实是 mock，那就取消 mock 或删掉这条断言。

```typescript
// ✅ 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 的存在
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**使用者的纠正：**"我们是在测 mock 的行为吗？"

**在正确的层级上 mock。** 替换真实方法之前，先弄清它的每一个副作用；mock 掉慢的或外部的操作，让测试依赖的部分保持真实。拿不准时，先对着真实实现跑这个测试，观察实际需要发生什么。

```typescript
// ❌ mock 吞掉了重复检测要读的那次配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 慢的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**让替身足够具体。** 当参数、调用次数或顺序是契约的一部分时，就对它们做断言 —— 一个什么都接受的 fake 什么也验证不了。给每个分支（成功、错误、畸形输入）各准备自己的 fixture 或 spy，这样错误的分支就无法满足断言。

**完整镜像真实数据。** 按现实中存在的完整结构来 mock —— 所有有文档的字段 —— 而不只是你的测试会读的那些。当下游代码读取被省略的字段时，残缺的 mock 会静默失败：测试通过，集成却坏了。

**生产类只带生产方法。** 只有测试需要的清理逻辑放在测试工具里，绝不要做成生产类上的 `destroy()`。问自己：这个方法只有测试在调用吗？这个类拥有该资源的生命周期吗？答案是否 → 放进测试工具。

**宁可要真实组件，也不要复杂 mock。** 当 mock 的搭建比测试逻辑还大、mock 缺少真实组件拥有的方法，或者 mock 一改测试就坏时，改用真实组件的集成测试。**使用者的问题：**"这里真的需要用 mock 吗？"

### 把关函数

```
在添加 mock 或测试辅助之前：
  列出真实方法的副作用；保留测试依赖的那些为真实 ——
  在它们下面那一层 mock 掉慢的/外部的操作。

  mock 的返回值要完整镜像真实结构。

  只有测试会调用的方法，放在测试工具里，而不是生产代码里。

  正要断言 mock 本身？
    取消 mock，或者删掉这条断言。
```

## 测试与实现一起交付

TDD 循环 —— 失败的测试、最小的实现、重构 —— 才是"完成"的含义。只交付该行为需要的测试，仅此而已：平凡代码和写给人看的散文一个都不需要，而为了走流程写的测试，会让你永远付出维护成本。

## 变异检查

在收尾之前，在脑子里对生产代码做变异；每一个现实可行的变异，都应该至少让一个测试失败：

- 错误的常量或参数
- 错误的分支处理
- 缺失的状态变更或副作用
- 空返回或默认返回
- 对零、空、nil、未授权或畸形输入缺少校验

没有任何测试抓住的变异，说明那段行为没有保护 —— 或者说明那个测试是同义反复。

## 快速参考

| 当你…… | 要做的事 |
|-------------|-----|
| 写任何测试 | 点明它能抓住的那处破坏 —— 是 bug，而不是决定 |
| 构造期望值 | 手工推导；绝不用被测代码来算 |
| 测脚本或文档 | 运行它 / 对它的消费者施加压力测试；绝不用 grep 搜它的文本 |
| 想给依赖写测试 | 测你自己的边界契约，而不是它们文档化的机制 |
| 想对 mock 出来的元素做断言 | 测真实组件，或者取消 mock |
| 即将 mock 一个方法 | 弄清它的副作用；mock 慢的/外部的那个层级 |
| 构造 mock 返回值 | 完整镜像真实结构 |
| 需要只有测试用的清理逻辑 | 放进测试工具 |
| 发现 mock 搭建在膨胀 | 改用真实组件的集成测试 |
| 完成一个测试文件 | 跑一遍变异检查 |

## 警告信号

- 搭建和断言共用同一个对象，保证了它们相等
- 这个测试只能通过 panic、崩溃或选择器缺失来失败
- 这个测试在每一次刻意改动时都失败，却从不对意外损坏报警
- 期望值藏在循环、builder 或辅助函数后面
- 这个测试 grep 源码文本，或者断言已删除的符号仍然不存在
- 如果只剩框架，这个测试依然有意义
- 这个测试为覆盖率而存在，不检查任何副作用或结果
- 断言检查的是 `*-mock` 测试 ID，或者你一删掉 mock 它就失败
- 某个方法只有测试文件在调用
- mock 搭建占了测试的一半以上，或者你说不清为什么需要这个 mock
- "只为保险起见"而 mock
