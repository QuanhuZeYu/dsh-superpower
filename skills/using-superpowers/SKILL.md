先根据用户目标、技能描述与当前误差判断适用性。用户点名或任务明确匹配的技能必须加载；仅有关键词相似或遥远可能性时，不扩大加载范围。信息不足以选择流程时，先做最小只读观测，再决定需要哪个技能。

## 规则

**在执行适用流程前，加载被点名或明确匹配的技能。** 加载后核对适用边界；不匹配就停止套用，并保留已经取得的有效证据。同一会话已读版本无需重复加载，除非版本或任务发生变化。

**进入 plan mode 之前：** 仅当任务需要创建或改变行为、且设计尚未明确时加载 brainstorming；纯阅读、审查或已有明确方案不因切换模式而新增设计流程。

声明正在使用哪个技能及目的。多步骤工作把实际适用的动作合并进现有 todo；不为重复清单另造流程，也不把不适用项变成待办。

## 技能优先级

多个技能同时适用时，流程类技能优先 —— 它们决定做事方式，然后由实现类技能（前端设计等）去落地。brainstorming 与 systematic-debugging 是 Superpowers 最常用的流程技能，但这条规则对所有流程技能都成立。

**元层最先：** 只要任务不是一句话能做完的，先加载 `control-loop` 技能。它管"你怎么知道自己在收敛"（观测、误差、小步、反馈、重评），其它技能管具体流程；执行中反馈异常时，回到它。加载技能是为了选择最小有效流程，不是为了增加重复确认。

- "我们来做个 X" → 先 brainstorming，再用实现类技能。
- "修一下这个 bug" → 先 systematic-debugging，再用领域技能。
- 纯阅读、错字修正、格式调整等不改变行为的可逆文档维护，不因“创造性工作”触发 brainstorming；在已明确授权且范围不变时直接执行，并验证 diff。
- 已有授权覆盖当前动作时，不重复询问同一授权；只有目标、范围、风险或必要输入发生变化时才暂停重评。

## 选择开发模式

开始实现或修复前按任务选择，记录在简报并传给实现者、评审者；不用为每个任务重复请求授权。

- 使用者明确选择时遵循该模式；已有项目约定时沿用它。
- 没有指定时：稳定契约与纯逻辑用 `test-driven-development`；依赖真实环境、设备、交互、时序或集成的行为用 `runtime-driven-development`。混合任务按需要拆分，每段明确模式。
- 运行时模式允许最小可运行实现、日志探针与开发期断言，再用实机反馈定位和验证；不受 TDD 的先行失败测试/删除实现条款约束。
- `systematic-debugging` 的根因调查与 `verification-before-completion` 的证据要求仍适用于两种模式；代码阅读只能提出运行假设，不能冒充实机结果。

## 校准流程

- 技能选择应说明它缩小哪个误差或信息缺口；技能存在本身不是使用理由。
- 发现新增依赖或不可逆后果时重评；观测证明范围缩小时，可收缩流程，保留验收和必要授权。
- 反馈与预测不符时停止扩大改动，更新假设并执行最小实验或修正；不确定性通过行动消除。
- 流程投入增加而没有新证据时，检查是否重复加载、确认或评审；不要用更多流程代替诊断。

## 平台适配

本副本只针对 DeepSeek Harness (DSH) 适配。

读 `references/dsh-tools.md`，那里有 DSH 的工具映射与本平台特有规则（命令执行、子代理、plan mode，以及 DSH 不具备的机制）。

## 用户指令

用户指令（`AGENTS.md`、`~/.dsh/AGENTS.md`、直接请求）优先于技能，技能优先于默认行为。只有当使用者明确要求时，才可以跳过技能流程或指令。
