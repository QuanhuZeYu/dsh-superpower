# 完成前验证

## 概览

**核心原则：永远先有证据，再有结论。**

**违背这条规则的字面，就是违背它的精神。**

## 铁律

```
没有新鲜的验证证据，不得声称完成
```

如果本轮消息里你没有真正运行过验证命令，就不能声称它通过。

## 门禁流程

```
在声称任何状态或表达满意之前：

1. 确定：哪条命令能证明这个结论？
2. 运行：完整执行该命令（全新、完整）
3. 阅读：看完整输出，检查退出码，数清失败数
4. 核对：输出是否支撑该结论？
   - 否：用证据说明真实现状
   - 是：带着证据下结论
5. 只有到这一步：才下结论

跳过任何一步 = 撒谎，不是验证
```

## 常见失败

| 结论 | 需要什么 | 不足以支撑 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 上一次的运行结果、"应该能过" |
| Linter 干净 | Linter 输出：0 错误 | 局部检查、外推结论 |
| 构建成功 | 构建命令：退出码 0 | Linter 通过、日志看着正常 |
| Bug 已修复 | 复现原始症状的测试：通过 | 改了代码、假定已修好 |
| 回归测试有效 | 验证过红-绿循环 | 测试只通过了一次 |
| 子代理已完成 | 版本库 diff 显示改动 | 子代理自报"成功" |
| 需求已满足 | 逐条对照清单 | 测试通过 |

## 危险信号 —— 立刻停

- 使用"应该"、"大概"、"似乎"
- 在验证之前表达满意（"太好了"、"完美"、"搞定了"等）
- 未经验证就要 commit / push / 发起 PR
- 相信子代理的成功汇报
- 依赖局部验证
- 想着"就这一次"
- 累了、只想赶紧收工
- **任何暗示成功、却没跑过验证的措辞**

## 反自我合理化

| 借口 | 现实 |
|--------|---------|
| "现在应该能跑了" | 去运行验证 |
| "我有把握" | 把握 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 过了" | Linter ≠ 编译器 |
| "子代理说成功了" | 独立验证 |
| "我累了" | 疲惫不是理由 |
| "局部检查够了" | 局部什么都证明不了 |
| "换个说法，规则就不适用了" | 精神重于字面 |

## 关键范式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "所有测试通过"
❌ "现在应该过了" / "看起来没问题"
```

**回归测试（TDD 红-绿）：**
```
✅ 写测试 → 运行（通过）→ 撤销修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了一个回归测试"（没有做红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] "构建通过"
❌ "Linter 过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建清单 → 逐条核对 → 报告缺口或完成
❌ "测试通过，阶段完成"
```

**子代理委派：**
```
✅ 子代理报告成功 → 看版本库 diff → 核对改动 → 报告真实状态
❌ 直接相信子代理的报告
```

## 何时适用

**以下情况永远适用：**
- 任何形式声称成功 / 完成
- 任何表达满意的措辞
- 任何关于工作状态的正面陈述
- 提交、创建 PR、宣布任务完成
- 进入下一个任务
- 委派给子代理

**规则覆盖：**
- 原话
- 改写与同义词
- 暗示成功
- 任何暗示完成 / 正确的表达
