# 完成前验证

**铁律：没有针对当前版本的最新验证证据，不得声称完成。**

结论必须与实际取得的反馈严格匹配：已通过约定验证就直接报告通过；存在缺口就具体指出并补跑，不用反复免责声明替代验证。

## 门禁步骤

在声称实现完成、缺陷修复或检查通过前，依次完成：

1. **确定验证通道：** 明确哪条命令或哪次目标实例操作能证明该结论。
2. **在当前版本执行：** 针对最新改动完整运行，记录版本、输入与执行位置。
3. **核对原始反馈：** 检查退出码、失败计数、目标路径命中及实际输出（仅转述时须注明来源，不得冒充亲自运行）。
4. **据实下结论：** 证据支撑则带着结果报告完成；不支撑则修代码或修观测通道后复测。

**设计交付与运行结果分开：** 规格与计划完成自检后即可报告“规格/计划已完成”，无需在每节重复声明“代码尚未运行”；进入实现阶段后则必须凭真实运行证据验收。

## 证据充分性速查

| 要声称的结论 | 必需的真实证据 | 不足以支撑的借口 |
| --- | --- | --- |
| 测试 / 构建 / Linter 通过 | 对应命令在当前树上的最新输出（0 失败 / 退出码 0） | 之前跑过、Linter 过了所以构建没问题、“改动很小应该能过” |
| Bug 已修复 | 原始症状记录 + 最终版本同场景测试或实机复测通过 | 代码改了、编译过了、没看到报错日志 |
| 运行时模式完成 | 目标实例路径命中、同场景结果、关闭临时探针后的交付配置复测 | 静态分析、离线模拟、单次未复现 |
| 子代理已完成工作 | 版本库 `git diff` 与测试/实机证据核对无误 | 子代理自己在报告里说“成功” |
| 需求已全部满足 | 逐条对照规格/计划清单核对改动与验证记录 | “测试套件绿了所以需求做完了” |
