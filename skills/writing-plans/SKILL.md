# 编写计划

## 概览

编写全面的实施计划，假定执行工程师对我们的代码库零上下文、品味也靠不住。把他们需要知道的一切都记录下来：每个任务要动哪些文件、代码、测试、可能需要查阅的文档、怎么测试。把整份计划拆成小颗粒任务交给他们。DRY。YAGNI。TDD。频繁 commit。

假定他们是熟练的开发者，但对我们的工具链和问题域几乎一无所知。假定他们对好的测试设计也不太在行。

**开始时宣告：**"我正在使用 writing-plans 技能来编写实施计划。"

**上下文：** 如果在隔离的 worktree 中工作，该 worktree 应当是在执行阶段由 `using-git-worktrees` 技能创建的。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （使用者对计划位置的偏好优先于此默认值）

## 范围检查

如果 spec 覆盖多个相互独立的子系统，它本应在 brainstorming 阶段被拆成多个子项目 spec。如果当时没拆，就建议把它拆成若干份独立计划 —— 每个子系统一份。每份计划都应能独立产出可运行、可测试的软件。

## 文件结构

在定义任务之前，先规划出要新建或修改哪些文件、每个文件负责什么。拆分的决策就是在这里定下来的。

- 设计边界清晰、接口定义明确的单元。每个文件都应有一个明确的职责。
- 对你能一次性放进上下文的代码，你推理得最准；文件职责聚焦时，你的改动也更可靠。优先选择更小、更聚焦的文件，而不是什么都干的大文件。
- 总是一起改动的文件应该放在一起。按职责拆分，而不是按技术分层拆分。
- 在已有代码库中，遵循既有模式。如果代码库本身就用大文件，不要单方面重构 —— 但如果你正在修改的文件已经臃肿难用，在计划里包含一次拆分是合理的。

这个结构决定任务如何拆分。每个任务都应产出能独立成立的、自成一体的改动。

## 任务规模校准

任务是最小的单元：它自带完整的测试循环，并且值得让一位全新的评审者把关。划定任务边界时：把环境搭建、配置、脚手架和文档步骤并入其交付物需要它们的那个任务；只有当评审者可以合理地否决一个任务、同时通过它相邻的任务时，才在那里拆分。每个任务都以一个可独立测试的交付物收尾。

## 小颗粒任务粒度

**每一步只做一个动作（2-5 分钟）：**
- "编写会失败的测试" - 一步
- "运行它，确认它失败" - 一步
- "实现最小代码，让测试通过" - 一步
- "运行测试，确认它们通过" - 一步
- "Commit" - 一步

## 计划文档抬头

**每份计划都必须以这个抬头开头：**

```markdown
# [功能名称] 实施计划

> **面向 agent 执行者：** 必需子技能：使用 subagent-driven-development（推荐）或 executing-plans，按任务逐个实施本计划。步骤用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话说明要构建什么]

**架构：** [2-3 句话说明实现思路]

**技术栈：** [关键技术/库]

**Spec：** [本计划所实现的那份 spec/设计文档的路径 —— 计划是从 spec 出发论证的，
所以 spec 要随计划一起流动；执行者会两份都读]

## Global Constraints

[spec 中项目级的要求 —— 版本下限、依赖限制、命名与文案规则、平台要求 ——
每条一行，数值原样照抄 spec。每个任务的要求都隐含包含本节。]

## Review Focus

[spec 暗示、但没有任何任务的测试覆盖到的五类输入或失败模式 —— 它们最可能坑到
使用这个软件的人 —— 每条一行，点明输入或条件，以及一个理性人会期待的行为，
最可能的排在最前面。spec 是一份愿景文档：它说的是软件必须做什么，而不是它会
遇到的一切；它对某个输入保持沉默，不等于允许那个输入把程序搞崩。把 spec 摊在
面前，在这里把这份清单一次写完。然后为每一行补上钉住它的测试，加到拥有那段
代码的任务里，用该任务自己的步骤风格。]

---
```

## 任务结构

````markdown
### 任务 N：[组件名]

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[本任务用到前面任务的哪些东西 —— 精确的签名]
- 产出：[后续任务依赖的东西 —— 精确的函数名、参数与返回类型。任务的实现者
  只能看到自己那一个任务；这个区块就是他们了解相邻任务所用名称与类型的途径。]

- [ ] **步骤 1：编写会失败的测试**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **步骤 2：运行测试，确认它失败**

运行：`pytest tests/path/test.py::test_name -v`
预期：FAIL，报错 "function not defined"

- [ ] **步骤 3：编写最小实现**

```python
def function(input):
    return expected
```

- [ ] **步骤 4：运行测试，确认它通过**

运行：`pytest tests/path/test.py::test_name -v`
预期：PASS

- [ ] **步骤 5：Commit**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 禁止占位符

每一步都必须包含工程师真正需要的内容。下面这些是**计划失败** —— 永远不要写：
- "TBD"、"TODO"、"稍后实现"、"细节待补"
- "加上适当的错误处理" / "加校验" / "处理边界情况"
- "为以上内容写测试"（而没有实际的测试代码）
- "与任务 N 类似"（把代码重复写出来 —— 工程师可能不按顺序读任务）
- 只描述要做什么、却不展示怎么做的步骤（代码类步骤必须有代码块）
- 引用了任何任务里都没有定义的类型、函数或方法

## 自检

写完整份计划之后，用全新的眼光重读 spec，把计划与它逐条对照。这是你自己执行的清单 —— 不是派发子代理。

**1. spec 覆盖：** 略读 spec 的每一节/每项要求。你能指出实现它的任务吗？列出所有缺口。

**2. 占位符扫描：** 在计划里搜索危险信号 —— 上面"禁止占位符"一节中的任何模式。修掉它们。

**3. 类型一致性：** 你在后面任务里用到的类型、方法签名和属性名，与你在前面任务里定义的一致吗？任务 3 里叫 `clearLayers()`、任务 7 里却叫 `clearFullLayers()` 的函数就是一个 bug。

**4. Review Focus：** 对 spec 暗示的每一类输入或失败模式，是否都有某个任务的测试覆盖到它？最可能坑人的五个未覆盖项写进 Review Focus 一节，其中每一行都要把对应的测试加到拥有那段代码的任务里。一节为空意味着你检查过、确实没有，而不是你跳过了这项检查。

发现问题就地修正。不需要重新自检 —— 改完继续往下走。如果发现某条 spec 要求没有对应任务，就补上该任务。

## 执行交接

计划保存并自检完成后，把它链接给你的使用者阅读。如果对方已经明确给出了执行方式，就请其审阅计划、确认它抓住了他们想要的；在开始实现之前等待这次审阅，然后采用既定的方式。否则，请对方审阅计划，并在实现前选定一种执行方式。

**当尚未给出执行方式时：**

**"计划已完成，保存在 `docs/superpowers/plans/<filename>.md`。请审阅这份计划。你更希望采用哪种执行方式？**

- **子代理驱动（Subagent-driven）** - 每个任务由一个全新的子代理实现，并在下一个任务开始前由一位全新的评审者检查，最后再做一次整条分支的评审。最彻底；代价是每个任务、每次评审都要消耗一份全新上下文。
- **原生执行（Native）** - 我在本会话里亲自实现每一个任务，按本 harness 的方式推进工作，最后让一位用最强模型的全新评审者检查整条分支。最便宜、最快；在结束之前没有独立评审。由于设计由计划承载，用中等档位的会话模型也能跑得很好。

**对于这份计划，我推荐 <二者之一>，因为 <用计划里的一句话说明：任务之间在接口上有多依赖、任务有多少个、上线后出错会付出多大代价>。这份计划抓住你想要的了吗？我们该用哪一种？"**

**当已经给出执行方式时：**

**"计划已完成，保存在 `docs/superpowers/plans/<filename>.md`。请审阅这份计划。它抓住了你想要的吗？"**

**如果选择了子代理驱动：**
- **必需子技能：** 使用 subagent-driven-development

**如果选择了原生执行：**
- **必需子技能：** 使用 executing-plans
