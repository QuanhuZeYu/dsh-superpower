# 编写计划

编写可直接实施的计划，向执行者交代必要上下文、已选方案、目标文件、跨任务接口契约与验证方式。计划保存至 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`（用户指定路径优先）。

## 核心原则

- **先规划文件结构，再拆任务：** 按职责划分边界清晰、可一次装入上下文的小文件；若触碰已臃肿文件，将拆分纳入计划。
- **按可独立验证的纵向行为拆任务：** 先跑通代表性真实链路，再扩展复杂分支；环境搭建、配置和文档并入消费它们的任务。若 spec 含多个独立子系统，建议按子系统拆成多份独立计划。
- **作者解方案歧义，执行者定局部可逆细节：** 计划定死职责、依赖、跨任务接口签名与验收；内部算法与普通参数交执行者沿契约决定，不把不确定性变成逐层防御或额外审批。
- **严禁占位符：** 禁止出现 `TBD / TODO / 稍后实现`、禁止无具体触发路径的“加上适当错误处理/校验”、禁止无输入与期望的“为以上内容写测试”、禁止引用任何任务都未定义的函数或类型。

## 计划文档模板

每份计划必须包含以下抬头，并为每个任务明确标注 `test-driven-development` 或 `runtime-driven-development`：

```markdown
# [功能名称] 实施计划

> **面向 agent 执行者：** 必需子技能：使用 subagent-driven-development（推荐）或 executing-plans 逐任务实施。步骤用 `- [ ]` 跟踪。

**目标：** [一句话说明要构建什么]
**架构：** [2-3 句话说明实现主线]
**技术栈：** [关键技术/库]
**开发模式：** [默认模式；每个任务正文须再次写明]
**Spec：** [spec 文档路径 —— 冲突裁决的最高权威]

## Global Constraints
[逐字照抄 spec 中的项目级硬约束：版本下限、依赖限制、命名规则、平台要求]

## Review Focus
[仅列任务验收尚未覆盖且有具体依据的关注点：触发路径 → 可见后果 → 最小验证 → 所属任务。无额外项时写“按任务验收，无额外项”。]

---

### 任务 N：[组件/行为名]

**开发模式：** test-driven-development | runtime-driven-development

**文件：**
- 新建 / 修改 / 测试：`exact/path/to/file:lines`

**接口：**
- 消费：[本任务调用的前序任务产物 —— 精确签名]
- 产出：[后续任务依赖的本任务产物 —— 精确函数名、参数与返回类型]
```

### 任务步骤写法（二选一）

- **TDD 模式步骤：**
  1. `- [ ] 步骤 1：跑通最小真实闭环`（写明生产入口、输入、预期结果与运行命令；已有实现直接复用，不删正确代码）
  2. `- [ ] 步骤 2：运行必要反例并修正`（按合同与边界选少量反例，给独立字面量期望；直接通过则如实记录，失败则修根因）
  3. `- [ ] 步骤 3：回归与提交`（重跑受影响路径与项目必需检查，达标即 commit）
- **运行时模式步骤（`runtime-driven-development`）：**
  1. `- [ ] 确认目标实例与场景并运行基线`（记录版本/实例与复现入口，无测试文件时不编造文件）
  2. `- [ ] 布置探针/开发期断言并触发目标路径`（验证探针命中，从实际输出定位偏差并做最小修改）
  3. `- [ ] 同场景及交付配置复测并提交`（关闭临时诊断后实测确认，跑项目必需检查后 commit）

## 自检与执行交接

写完计划后对照 spec 自检并就地修复：(1) **spec 要求全覆盖**；(2) **零占位符**；(3) **跨任务类型与函数签名严格一致**；(4) **Review Focus 落实到具体任务**。

**交接：** 提供计划文件链接，沿用已有授权与审阅约定。已授权自主实施时采用既定执行方式；未指定时按任务依赖、成本与可用工具自行选择，说明理由并加载对应技能继续。仅在用户要求此节点审阅，或缺少涉及必要偏好、额外成本授权或风险变化的决定时，呈现以下选项并给出推荐：
- **子代理驱动（`subagent-driven-development`）：** 每任务独立子代理实现 + 逐任务评审 + 最终整分支评审（最彻底，消耗多份上下文）。
- **内联执行（`executing-plans`）：** 本会话亲自逐任务实现 + 最终整分支评审（更快更省，靠台账与运行证据把关）。
