# 编写计划

## 概览

编写可直接实施的计划，给执行工程师必要上下文、已选方案、要改的文件与接口，以及验证方式。按可独立验证的行为拆任务，细节深度与改动复杂度相称。DRY。YAGNI。按任务选择 TDD 或运行时驱动开发。频繁 commit。

把执行者当作能作局部判断的开发者：作者负责解决方案层面的歧义，执行者可沿契约处理可逆实现细节。计划继承 spec 的有限验收，不把不确定性翻译成逐层检查、泛化兜底或额外审批。每个新增防御动作应对应具体触发路径与用户结果，已有接口负责的处理直接复用。

**开始时宣告：**"我正在使用 writing-plans 技能来编写实施计划。"

**上下文：** 如果在隔离的 worktree 中工作，该 worktree 应当是在执行阶段由 `using-git-worktrees` 技能创建的。

**计划保存到：** `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`
- （使用者对计划位置的偏好优先于此默认值）

## 范围检查

如果 spec 覆盖多个相互独立的子系统，它本应在 brainstorming 阶段被拆成多个子项目 spec。如果当时没拆，就建议把它拆成若干份独立计划 —— 每个子系统一份。每份计划都应能独立产出可运行、可测试的软件。

## 先跑通真实链路

按可观察的业务链路安排交付，用代表性输入覆盖关键职责，再扩展复杂内容。独立交付的子系统可拆计划，同一链路的技术层不因分层本身拆成互不接通的子项目。

计划确定职责、依赖、跨任务接口契约与验收，执行者沿契约选择普通可逆参数和内部算法，不逐项交用户审批。影响目标或外部契约的新取舍再返回设计。计划是实施工具，不把施工细节复制为长期规格。

## 文件结构

在定义任务之前，先规划出要新建或修改哪些文件、每个文件负责什么。拆分的决策就是在这里定下来的。

- 设计边界清晰、接口定义明确的单元。每个文件都应有一个明确的职责。
- 对你能一次性放进上下文的代码，你推理得最准；文件职责聚焦时，你的改动也更可靠。优先选择更小、更聚焦的文件，而不是什么都干的大文件。
- 总是一起改动的文件应该放在一起。按职责拆分，而不是按技术分层拆分。
- 在已有代码库中，遵循既有模式。如果代码库本身就用大文件，不要单方面重构 —— 但如果你正在修改的文件已经臃肿难用，在计划里包含一次拆分是合理的。

这个结构决定任务如何拆分。每个任务都应产出能独立成立的、自成一体的改动。

## 任务规模校准

任务是可独立评估的行为增量，自带与开发模式相符的验证闭环。划定任务边界时：把环境搭建、配置、脚手架和文档步骤并入其交付物需要它们的那个任务；只有当评审者可以合理地否决一个任务、同时通过它相邻的任务时，才在那里拆分。每个任务都以可独立验证的交付物收尾，不要求一律编写自动化测试。

## 开发模式与验证路径

按 `using-superpowers` 选择模式，在每个任务正文写明并随简报传递，不能只放计划抬头。自动模式使用下方最小闭环与反例模板；运行时模式使用 `runtime-driven-development`，写清目标实例、操作输入、观测点及必要实机复测。两种模式都不强制先行失败测试或删除正确实现。模式变化需说明原因；不能把两套顺序都当作必做。

## 小颗粒任务粒度

**按能执行并取得反馈的动作划分步骤，不强制固定分钟数，也不把每步变成审批点。下面仅为选择 TDD 时的顺序示例：**
- 建立或复用最小真实路径并实际运行
- 根据合同选择必要反例，运行并据误差修正
- 回归受影响路径与项目必需检查，按授权交付

已跑通的实现保留；多个动作可合并，不为这份示例再增加阶段门禁。

## 计划文档抬头

**每份计划都必须以这个抬头开头：**

```markdown
# [功能名称] 实施计划

> **面向 agent 执行者：** 必需子技能：使用 subagent-driven-development（推荐）或 executing-plans，按任务逐个实施本计划。步骤用复选框（`- [ ]`）语法跟踪。

**目标：** [一句话说明要构建什么]

**架构：** [2-3 句话说明实现思路]

**技术栈：** [关键技术/库]

**开发模式：** [默认模式；每个任务再次写明 TDD 或 runtime-driven-development]

**Spec：** [本计划所实现的那份 spec/设计文档的路径 —— 计划是从 spec 出发论证的，
所以 spec 要随计划一起流动；执行者会两份都读]

## Global Constraints

[spec 中项目级的要求 —— 版本下限、依赖限制、命名与文案规则、平台要求 ——
每条一行，数值原样照抄 spec。每个任务的要求都隐含包含本节。]

## Review Focus

[只列尚未被任务验收覆盖、且有具体依据的关注点：触发路径或真实外部边界 → 可见后果 → 最小验证 → 所属任务。无需凑数；没有额外关注点时写“按任务验收，无额外项”。已由现有接口处理的错误注明复用即可。新发现确有行为缺口时补对应测试或实机操作；可选增强与未经证实的猜测不升级为任务门禁。]

---
```

## 任务结构

以下为 TDD 模板；运行时模式保留文件与接口区块，替换为后面的运行时步骤。

````markdown
### 任务 N：[组件名]

**开发模式：** test-driven-development

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py:123-145`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[本任务用到前面任务的哪些东西 —— 精确的签名]
- 产出：[后续任务依赖的东西 —— 精确的函数名、参数与返回类型。任务的实现者
  只能看到自己那一个任务；这个区块就是他们了解相邻任务所用名称与类型的途径。]

- [ ] **步骤 1：跑通最小真实闭环**

[写明生产入口、输入、可观察结果及实际运行方式；已有实现与运行证据直接复用，不删除重写。]

- [ ] **步骤 2：运行必要反例并修正**

[依据用户合同、已知故障或真实调用边界选少量反例，独立给出期望；反例通过如实记录，不凑失败。发现误差后做最小修正。]

- [ ] **步骤 3：回归与交付**

[重跑受影响的原路径与反例，完成项目必需检查；满足验收停止扩展，提交按已有授权。]
````

### 运行时模式步骤

任务中写 `开发模式：runtime-driven-development`。按目标场景填入以下步骤的具体命令或操作、预期结果与记录位置；没有测试文件时列出实机验证入口，不编造文件。

- [ ] 确认目标版本、实例与验收场景；运行现状，尚无实现则先建立最小可运行路径。
- [ ] 围绕一个待判定问题加日志/开发期断言，触发目标路径并验证探针有效。
- [ ] 从实际输出判断偏差，做最小修改；预期只是预测，失败与成功留待运行填写。
- [ ] 同场景实机复测，覆盖必要边界并运行项目要求的既有检查；能稳定自动化的部分按需沉淀回归。
- [ ] 清理或关闭临时诊断，在交付配置下复测；记录已验证范围和剩余缺口，再按计划提交。

Review Focus 的每个相关输入都要落实到运行场景与观测，不必一律转成自动化测试。手动设备操作写清动作和结果来源，不能用打印“PASS”的命令代替。

## 禁止占位符

每一步都必须包含工程师真正需要的内容。下面这些是**计划失败** —— 永远不要写：
- "TBD"、"TODO"、"稍后实现"、"细节待补"
- "加上适当的错误处理" / "加校验" / "处理边界情况"
- "为以上内容写测试"（却没有说明输入、预期行为及执行方式）
- "与任务 N 类似"（却没有必要上下文或可定位的公共契约）
- 缺少落地所需的行为、接口或验证说明；关键算法可给伪代码或示例，不强制预写完整实现
- 引用了任何任务里都没有定义的类型、函数或方法

## 自检

写完整份计划之后，用全新的眼光重读 spec，把计划与它逐条对照。这是你自己执行的清单 —— 不是派发子代理。

**1. spec 覆盖：** 略读 spec 的每一节/每项要求。你能指出实现它的任务吗？列出所有缺口。

**2. 占位符扫描：** 在计划里搜索危险信号 —— 上面"禁止占位符"一节中的任何模式。修掉它们。

**3. 类型一致性：** 你在后面任务里用到的类型、方法签名和属性名，与你在前面任务里定义的一致吗？任务 3 里叫 `clearLayers()`、任务 7 里却叫 `clearFullLayers()` 的函数就是一个 bug。

**4. Review Focus：** 核对约定验收。只把有具体触发路径和可见后果的真实缺口写入 Review Focus，归属对应任务并按模式补最小验证；已覆盖就结束，无额外项即可，不凑数量。

发现问题就地修正；缺任务就补齐。随后复核受影响的需求覆盖、接口消费与产出、依赖和验收步骤，确认修正没有留下新缺口。不重跑无关部分的自检，满足本阶段验收后交接。

## 执行交接

计划保存并完成受影响范围的自检后，提供文件链接，沿用当前会话的授权与评审约定。用户明确要求此节点审阅时等待；已经授权自主实施且目标、风险和范围未变时，采用既定执行方式继续。没有指定方式时，按任务依赖、成本和可用工具选择并说明；只有该选择涉及必要用户偏好、额外成本授权或风险变化时才询问。不得把“计划已写好”说成“用户已审阅”，也不因生成新文档而重复索要已有授权。

以下询问模板仅用于确实需要用户审阅或选择的情况。

**当尚未给出执行方式时：**

**"计划已完成，保存在 `docs/superpowers/plans/<filename>.md`。请审阅这份计划。你更希望采用哪种执行方式？**

- **子代理驱动（Subagent-driven）** - 每个任务由一个全新的子代理实现，并在下一个任务开始前由一位全新的评审者检查，最后再做一次整条分支的评审。最彻底；代价是每个任务、每次评审都要消耗一份全新上下文。
- **原生执行（Native）** - 我在本会话里亲自实现每一个任务，按本 harness 的方式推进工作，最后让一位用最强模型的全新评审者检查整条分支。最便宜、最快；在结束之前没有独立评审。由于设计由计划承载，用中等档位的会话模型也能跑得很好。

**对于这份计划，我推荐 <二者之一>，因为 <用计划里的一句话说明：任务之间在接口上有多依赖、任务有多少个、上线后出错会付出多大代价>。这份计划抓住你想要的了吗？我们该用哪一种？"**

**当已经给出执行方式时：**

**"计划已完成，保存在 `docs/superpowers/plans/<filename>.md`。请审阅这份计划。它抓住了你想要的吗？"**

**如果选择了子代理驱动：**
- **必需子技能：** 使用 subagent-driven-development

**如果选择了原生执行：**
- **必需子技能：** 使用 executing-plans
